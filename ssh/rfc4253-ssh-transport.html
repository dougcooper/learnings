SSH Transport

The bottom layer of the SSH protocol stack. Its job is narrow but load-bearing: open a TCP connection, agree on cryptography with the server, and turn that into an encrypted, integrity-protected channel that the layers above — user authentication (RFC 4252) and multiplexed sessions (RFC 4254) — ride on. Server authentication is built into the key exchange: the server signs the handshake with its host key, and the client decides whether to trust that key out-of-band. Everything else SSH does assumes this channel already exists and is untampered.

T. Ylönen SSH Comms Security C. Lonvick (ed.) Cisco Protocol 2.0 Port 22
The whole spec in five lines
  • SSH is three protocols stacked. The transport layer (this RFC) builds the encrypted pipe; userauth (4252) then proves who you are over it; the connection layer (4254) opens channels for your shell, file copy, and port forwards. Each layer speaks to the one below through a single message type.
  • Everything starts with one plaintext line over TCP: each side sends SSH-2.0-softwareversion terminated by CR LF before any binary data. The protocol version you advertise is what gates compatibility.
  • Both sides immediately send SSH_MSG_KEXINIT listing, in order, the algorithms they support — ten name-lists, chosen separately for each direction. The first algorithm the client lists that the server also lists, wins.
  • Key exchange is Diffie-Hellman: the client sends e = g^x, the server replies with f = g^y and signs the exchange hash H with its host key. The client checks that host key out-of-band — the one place a human, or a known_hosts file, enters the protocol.
  • Once both sides send SSH_MSG_NEWKEYS, every following packet is encrypted and MACed. The packet frame is fixed: length, padding-length, payload, random padding, MAC — and the MAC covers a 32-bit sequence number that is never reset, not even when the keys are renegotiated.

01 What the transport layer is

SSH-2 is not one protocol but a suite of five RFCs, and the division of labour is deliberate. The transport layer does only what has to happen before anything else is safe to say: it authenticates the server, sets up encryption and integrity, and hands a clean channel upward. Who you are is the next layer's problem, and that ordering is the point — user passwords and keys never travel before the pipe is protected.

What transport authenticates

The server, always

The key exchange binds the server's long-term host key into the shared secret. So when the handshake finishes, the client knows the channel is private and that the other end is whoever holds that host key. The client is not authenticated here — that is deferred to RFC 4252 on purpose.

What it does not do

No reliability, no framing of your data

Transport rides on TCP, so it inherits TCP's ordered, reliable byte stream. It does not retransmit or order anything itself. It also does not know what a "shell session" is — it just carries the SSH_MSG_USERAUTH and channel messages the upper layers put inside packets.

Why the split exists
Authentication is a separate layer so it can fail, retry, and offer multiple methods without tearing down the encrypted channel. If your public key is rejected, the transport connection stays up and you can fall back to a password — the expensive key exchange is not repeated. That is also why re-keying (§9) is designed to happen mid-stream without disturbing the layers above.
02 Connection setup and the version exchange

The transport connection is a TCP session (§4.1), by default to port 22. The moment it is open, each side transmits a single human-readable identification string — in the clear, before any binary protocol byte. That line does two jobs: it fixes the protocol version, and it gives both endpoints the strings they will later fold into the exchange hash to prove the handshake was not tampered with.

§4.2 — the identification string
SSH-protoversion-softwareversion SP comments CR LF
      ↑            ↑                ↑          ↑
      MUST be "2.0"      printable ASCII,        optional;       one CR (13)
      for SSH-2          no whitespace, no '-'   needs the SP     then one LF (10)

// max 255 bytes including CR and LF; a NUL byte MUST NOT be sent.
// real-world examples:
  SSH-2.0-OpenSSH_9.0
  SSH-2.0-OpenSSH_9.0exp1 Ubuntu-3ubuntu1
The rules that matter
  • Both sides send it independently, as soon as the TCP connection is up, and either side may send first. There is no request/response here — just two lines crossing.
  • A server MAY send banner lines before its identification string (legal warnings are the common case). They MUST NOT begin with SSH-, SHOULD be CR+LF terminated, and a client MUST be able to process or ignore them. A TCP-wrapper refusing the connection uses exactly this path.
  • Once a side has sent its identifier, it immediately starts key exchange — it does not wait to read the peer's line. The peer's identifier is read and stored for the hash, but the handshake is already in flight.
  • The strings are later concatenated into the exchange hash (V_C, V_S), so changing them mid-handshake would be detected. §5 handles the awkward case of one side speaking the old, incompatible SSH-1 protocol.
SSH-1 and SSH-2 are not the same protocol
The version field gates compatibility. SSH-1.99-... is the banner an implementation that speaks both versions traditionally sends; §5 then describes the fallback dance. But SSH-1 is a different, deprecated design with known flaws, and the §4.2 format here is specifically for protocol 2.0.
03 Algorithm negotiation — SSH_MSG_KEXINIT

Key exchange proper begins with both sides sending SSH_MSG_KEXINIT (message 20). It carries a 16-byte random cookie and ten name-lists — comma-separated algorithm identifiers, in the sender's order of preference. Five categories of algorithm are negotiated, and four of them are picked independently for each direction, so client→server and server→client can end up using different ciphers or MACs.

Name-listPicksPer direction?Notes
kex_algorithms key exchange method one e.g. diffie-hellman-group14-sha1. Also fixes the HASH function used everywhere downstream.
server_host_key_algorithms host key type one e.g. ssh-rsa. Constrained by the kex method — not every host key type is valid with every kex.
encryption_algorithms_c2s / _s2c cipher both Two lists. The chosen ciphers can differ per direction.
mac_algorithms_c2s / _s2c MAC both Two lists. Integrity algorithm, again per direction.
compression_algorithms_c2s / _s2c compression both Two lists. none is the norm; zlib is optional and off by default.
languages_c2s / _s2c language tag both Two lists. Almost always empty in practice.

§7.1 — the message also carries a first_kex_packet_follows boolean and a reserved uint32.

How a winner is chosen
  • For each name-list, the first algorithm in the client's list that also appears anywhere in the server's list is selected. Client preference wins; server order only matters for membership.
  • If there is no overlap in any category, the negotiation fails and the connection is closed with SSH_MSG_DISCONNECT. There is no second round — the lists are the lists.
  • Each side computes its choices and stores the other side's KEXINIT message verbatim, because that whole message (I_C / I_S) is fed into the exchange hash to authenticate the negotiation itself.
The optimistic guess, and its failure mode
first_kex_packet_follows is a single-bit optimisation: if true, the sender has already fired off its first key-exchange packet immediately after the KEXINIT, guessing that its first-listed kex algorithm will be chosen. If the guess was wrong, that follow-on packet must be silently ignored by both sides — the spec is explicit that a wrong guess costs a round trip but must not break the negotiation. Implementations that do not handle the "wrong guess" path correctly are a known source of interop hangs.
04 Diffie-Hellman key exchange

With algorithms agreed, both sides run Diffie-Hellman (§8). The idea of DH is that two parties each pick a secret random number, exchange a public value derived from it, and arrive at a shared secret K that an observer cannot compute — recovering it from the public values would mean solving the discrete logarithm problem, which is infeasible for a large enough group. SSH then binds that shared secret to the server's identity by having the server sign the exchange hash with its host key.

The exchange hash H

One value that binds everything

H hashes together the two version strings, both KEXINIT messages, the server's host key, the two DH public values, and the shared secret. Because it covers both sides' algorithm lists, an attacker cannot silently downgrade a party to a weaker cipher by editing a KEXINIT in transit — the signatures would no longer match.

The session identifier

H from the first exchange is special

The H produced by the first key exchange is also the session_id, and it is kept for the entire connection. Re-keying produces a fresh H but does not change the session id — it is the stable anchor the upper layers and extensions key off.

The MITM hole the spec admits to
§8 step 3 requires the client to verify that K_S "really is the host key for S" — via certificates or a local database. It then says plainly: the client MAY accept the key without verification, "however, doing so will render the protocol insecure against active attacks." That is the TOFU choice most users actually make: trust the key the first time you see it, and scream only if it changes. The cryptography is perfect; the human deciding "yes, connect anyway" is where a man-in-the-middle slips in.
Read these as 2006 defaults, not 2026 ones
Everything REQUIRED here is SHA-1 and 1024/2048-bit DH. SHA-1 collision pressure and the weakness of 1024-bit groups (group1) pushed the ecosystem to later RFCs: diffie-hellman-group14-sha256, the curve25519 exchange curve25519-sha256 / ecdh-sha2-nistp*, and RSA-SHA2 signatures (RFC 8332). §6.5 is explicit that more methods are defined in other documents — this RFC just sets the floor.
05 Key derivation and the session identifier

The DH step leaves both sides holding the shared secret K and the exchange hash H. Neither is used directly as an encryption key. Instead §7.2 derives six artifacts from them — a pair of initialisation vectors, encryption keys, and integrity keys, one of each per direction. An IV is the starting state a block cipher is seeded with so that encrypting the same plaintext twice produces different ciphertext; using distinct keys per direction stops one direction's traffic from helping break the other.

§7.2 — deriving the working keys
// from the DH step:
K  = g^(x*y) mod p            // shared secret, never transmitted
H  = HASH(V_C ‖ V_S ‖ I_C ‖ I_S ‖ K_S ‖ e ‖ f ‖ K)

// the session_id is H from the FIRST exchange — fixed for the connection's life
session_id = H   // unchanged on re-key

// six artifacts: HASH(K ‖ H ‖ X ‖ session_id), X drawn from {A..F}
A → initial IV    client→server     B → initial IV    server→client
C → encryption key c→s            D → encryption key s→c
E → integrity key  c→s            F → integrity key  s→c

// if a key is longer than one HASH output, extend by hashing the chain:
K1 = HASH(K ‖ H ‖ X ‖ session_id)
K2 = HASH(K ‖ H ‖ K1)
K3 = HASH(K ‖ H ‖ K1 ‖ K2)          // key = K1 ‖ K2 ‖ K3 ‖ ...
Why a fresh derivation per direction

Six separate values means the client's encryption key is not the server's, and neither integrity key is reused as an encryption key. §7.2 forbids using the same key for two purposes; the letter tags exist precisely to keep the domains apart. An IV that both sides seed from the same K/H but a different letter is how two directions stay cryptographically independent.

What feeds the hash

Every derived value mixes in K, H, a single letter, and the session_id. Because H already binds the version strings, both KEXINITs, and the host key, the derived keys inherit all of that authentication transitively — tamper with the negotiation and the keys come out wrong, so the channel just fails to decrypt.

The session id is the one permanent thing
Re-keying recomputes K, H, and all six working keys — but the session_id stays as the H from the very first exchange (§7.2, §9). That stability is what lets authentication and key-exchange extensions anchor to a value that does not move while everything else rotates.
06 Taking keys into use — SSH_MSG_NEWKEYS

Both sides have now derived the same keys, but they are not using them yet. The switch is fenced by a single message, SSH_MSG_NEWKEYS (21), defined in §7.3. It is the boundary in the stream between "old keys" and "new keys", and it exists because each side needs to know exactly when the other has started expecting ciphertext.

Sent under the old keys

Then the switch flips

SSH_MSG_NEWKEYS itself is sent using the current keys and algorithms. Only after sending it does an endpoint start encrypting outgoing packets with the new ones; and only after receiving it does it start decrypting incoming packets with the new ones.

Why a fence message at all

So failure is still speakable

If the new keys turn out to be broken, an endpoint needs to send a SSH_MSG_DISCONNECT its peer can still read. Keeping NEWKEYS under the old keys, and only switching on receipt, means there is always a half-open moment where a readable error can go out in either direction.

Before the first NEWKEYS, there are no keys
Until the first key exchange completes, the negotiated encryption and MAC are effectively "none": packets go on the wire in the clear with zero-length MAC. The KEXINIT and KEXDH messages themselves travel unencrypted — which is safe because the DH exchange is designed to be run in public, and the negotiation is authenticated after the fact through H.
07 The binary packet protocol

Every message — KEXINIT, a shell byte, a disconnect — rides inside one fixed frame defined in §6: a length, a padding-length, the payload, random padding, and a MAC. The padding does two jobs at once: it rounds the encrypted region up to a multiple of the cipher's block size, and it stops an observer from learning the payload's exact length. The MAC protects the whole thing plus an implicit sequence number.

§6 — the on-wire layout
uint32    packet_length      // = padding_length + len(payload) + len(padding); excludes itself and MAC
byte      padding_length     // n2
byte[n1]  payload            // n1 = packet_length - padding_length - 1
byte[n2]  random padding     // n2 = padding_length; ≥ 4, ≤ 255; SHOULD be random
byte[m]   mac                // m = MAC tag length; transmitted UNENCRYPTED

// total of (packet_length ‖ padding_length ‖ payload ‖ padding)
//   MUST be a multiple of max(cipher_block_size, 8)   — even for stream ciphers
// minimum packet: 16 bytes (or cipher block size, whichever is larger) + MAC

// MAC covers an implicit sequence number that is NOT on the wire:
mac = MAC(key, uint32(seq) ‖ unencrypted_packet)
//   seq starts at 0, +1 per packet, NEVER reset (even on re-key), wraps at 2^32
The sequence number is the subtle part

A 32-bit counter, never transmitted, incremented after every packet in either direction, and never reset — not even when keys are renegotiated. It is prepended to the packet inside the MAC input so that a recorded packet cannot be replayed or reordered: the receiver's counter will not match.

Padding is not just alignment

At least four bytes, never more than 255, and SHOULD be random. Beyond the block-size constraint, random padding hides the payload length from a passive observer. A packet that always padded to the minimum would leak the exact size of every keystroke — the reason implementations round up to a wider boundary.

What packet_length counts, and what it does not
packet_length is the size of everything from padding_length through the end of the random padding — not the packet_length field itself, and not the MAC. The MAC trails the packet, unencrypted, so a receiver reads the length first, knows where the encrypted region ends, then reads and verifies the MAC over the whole unencrypted-on-the-inside packet plus the sequence number.
Size limits are a connection-layer concern
§6.1: an implementation MUST handle an uncompressed payload up to 32768 bytes and a total packet up to 35000 bytes. Larger transfers are not one giant packet — the connection layer (RFC 4254) chunks application data across many of these frames, which is also what lets the receiver keep its buffers bounded.
08 Encryption, MAC and compression

§6.3–§6.2 name the algorithms the name-lists in KEXINIT can carry. The lists in this RFC are a 2006 snapshot: CBC block ciphers and the arcfour stream cipher for encryption, HMAC over SHA-1 or MD5 for integrity, and none or zlib for compression. CTR modes and encrypt-then-MAC arrived in later RFCs; the floor set here is what every implementation is guaranteed to speak.

A quick orientation for the non-cryptographer: CBC chains blocks so each one is XORed with the previous ciphertext block before encryption — the IV seeds the first block. HMAC is a keyed hash: it mixes a secret key into the message so only someone holding the key can produce a valid tag, and the receiver re-computes it to detect any change.

aes192-cbc / aes256-cbc block (CBC) OPTIONAL Larger AES key sizes, same mode.
blowfish-cbc, cast128-cbc, idea-cbc, serpent*-cbc, twofish*-cbc block (CBC) OPTIONAL A wide bench of alternatives; largely historical now.
arcfour stream OPTIONAL RC4. §6.3 warns it "has problems with weak keys, and should be used with caution."
none — OPTIONAL No encryption at all. "NOT RECOMMENDED." Exists for debugging, not for use.

§6.3 also asks that all ciphers SHOULD use an effective key length of 128 bits or more — 3des-cbc is the documented exception.

§6.2. Compression contexts are reset on re-key — the dictionary does not carry across a key change.

The parts that aged
3des-cbc as the REQUIRED cipher, SHA-1 everywhere, CBC with MAC-then-encrypt, and 1024-bit DH: each is a 2006 default the ecosystem has backed away from. CBC's interaction with SSH's MAC placement enabled the "SSH CBC insertion" attacks; CTR modes (RFC 4344), AES-GCM (RFC 5647), ChaCha20-Poly1305 (RFC 8709), and encrypt-then-MAC (RFC 6668) all came later and are what a modern client and server actually negotiate — on top of the floor this RFC sets.
09 Re-keying

A long-lived connection should not keep using the same keys forever. §9 lets either party start a fresh key exchange at any time by sending a new SSH_MSG_KEXINIT, and the whole §8 dance runs again — this time inside the already-encrypted channel. The new keys replace the old; the session identifier does not move.

§9 — re-key is just a second key exchange, with the same message flow, performed in place.

What resets
  • All six working keys and both IVs — recomputed from the new K and H.
  • The compression context — the zlib dictionary is thrown away and restarted.
  • The encryption state — a fresh cipher context is initialised with the new key and IV.
What does not
  • The session id — it stays as the first exchange's H, forever.
  • The sequence number — it keeps climbing. The counter is never zeroed, so a re-key is not a chance to reuse old nonce space.
  • The roles — whoever was client stays client. Re-key is symmetric, not a role swap.
When you should re-key
§9 recommends it after each gigabyte of transmitted data or each hour of connection time, whichever comes sooner. The motivation is key wear — the more ciphertext an attacker collects under one key, the more material they have to work with, and some modes have hard limits on how much traffic is safe under a single key before the integrity or confidentiality bounds get uncomfortably close.
10 Service request and the message set

Once NEWKEYS has flown in both directions, the channel is protected and the transport layer's own work is essentially done. The next move belongs to the upper layers: the client sends SSH_MSG_SERVICE_REQUEST (§10) naming the service it wants to run over the channel, and the server either accepts or disconnects.

The handoff

SSH_MSG_SERVICE_REQUEST

Carries one string: the service name. Two are reserved here — ssh-userauth (RFC 4252) and ssh-connection (RFC 4254). The server answers with SSH_MSG_SERVICE_ACCEPT, or refuses by sending SSH_MSG_DISCONNECT. After the implicit-authentication form of key exchange, the client must wait for the accept before sending anything else.

The lifecycle

auth, then connection

The usual sequence is ssh-userauth first — prove who you are — and then, once that succeeds, a second request for ssh-connection, which opens the channel layer your shell and file transfers actually use. Transport hosts both as plain services, oblivious to their contents.

The whole picture in one paragraph
Open TCP, swap a plaintext SSH-2.0- line, both fire a KEXINIT, run Diffie-Hellman, have the server sign the exchange hash with its host key and the client check that key out-of-band, derive six per-direction keys, flip to them with NEWKEYS, request ssh-userauth, and from then on everything you type is a payload inside a length-padded, MAC-with-sequence-number packet encrypted with those keys — until one side decides to re-key and runs the same dance again without dropping the channel.
