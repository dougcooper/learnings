Hybrid Key Exchange in TLS 1.3

Run two key exchange algorithms at once — one traditional, one post-quantum — and glue their outputs together. The session stays secure as long as at least one of them is still unbroken. The whole design is one idea repeated twice: concatenate.

D. Stebila U. Waterloo S. Fluhrer Cisco S. Gueron U. Haifa & Meta ISSN 2070-1721 Updates TLS 1.3 RFC 9846
The whole spec in four lines
  • Each traditional + next-gen pair gets one NamedGroup code point — an opaque identifier, negotiated like any other group.
  • Its key_exchange field is the components' public keys (or ciphertexts) concatenated, in the order the NamedGroup defines.
  • Its shared secret is the components' shared secrets concatenated, dropped into the existing key schedule unchanged.
  • No length prefixes anywhere — which is why every field must be fixed-length once the algorithm is pinned.
01 Why hybrid at all

Ideally you would pick one algorithm you trust forever. Quantum computers and cryptanalysis make that bet uncomfortable in both directions: traditional ECDH may fall to a quantum computer, and the new post-quantum algorithms are young and comparatively under-studied. Hybrid refuses to choose.

Threat

Harvest now, decrypt later

A passive adversary records handshakes and ciphertext today and decrypts them years from now, once the assumption breaks. Confidentiality is broken retroactively — so waiting for confidence in PQ algorithms is itself a risk.

Counter-risk

New algorithms are new

Most post-quantum candidates have not had the decades of scrutiny given to RSA and elliptic-curve Diffie-Hellman. Confidence in their fundamental security — and in specific parameter sets — is lower.

Resolution

Security of the strongest link

Combine both. The session key survives as long as one component holds. Early adopters get possible PQ security without giving up the security traditional algorithms already provide — or the FIPS compliance they may be required to keep.

Terminology
Traditional = widely deployed today, may be deprecated later (ECDH over secp256r1 or x25519, finite-field DH). Next-generation = not yet widely deployed, possibly less studied — including but not limited to post-quantum. A traditional + post-quantum pairing is a Post-Quantum Traditional Hybrid Scheme (RFC 9794); this document is deliberately broader, in case a cryptanalytic breakthrough — not a quantum computer — is what forces the move.

Note the vocabulary collision: TLS 1.3 calls key exchange algorithms "groups" because they were all Diffie-Hellman. Structures here still say "group" for algorithms that are neither DH-based nor groups.
Goals beyond the crypto
  • Backwards compatibility — hybrid-aware endpoints must still interoperate with endpoints and middleboxes that are not.
  • No extra round trips — in any of the three awareness scenarios below.
  • Minimal duplicate information — negotiating hybrid should not mean sending several public keys of the same type. (Section 8 shows where this goal bends.)
  • High performance, low latency — dominated by the component algorithms and by message size, so mostly out of scope here.

02 Everything is modelled as a KEM

To combine ECDH and a lattice scheme uniformly, the document treats both as key encapsulation mechanisms: three algorithms, one interface. Diffie-Hellman then slots in as a special case.

KeyGen() → (pk, sk)

Probabilistic. Produces a public key and a secret key. In DH terms: pick exponent x, publish g^x.

Encaps(pk) → (ct, ss)

Probabilistic. Takes the peer's public key, returns a ciphertext and a shared secret. In DH terms: pick y, send g^y, compute g^(xy).

Decaps(sk, ct) → ss

Deterministic. Recovers the same shared secret — or a distinguished error. In DH terms: compute g^(xy) from x and g^y.

The reuse trap
TLS 1.3 does not forbid reusing an "ephemeral" public key across sessions — some implementations do it, trading away forward secrecy. So any KEM used this way MUST be designed to stay secure when its public key is reused: IND-CCA2 security, or an IND-CPA scheme with a Fujisaki–Okamoto transform applied.
  • IND-CCA2 — shared secrets look random even to an attacker who can get arbitrary other ciphertexts decapsulated. Roughly: safe against an active attacker, safe to reuse the key pair.
  • IND-CPA — shared secrets look random given only the public key. Roughly: safe against a passive attacker, often one-shot only.
Some lattice-based IND-CPA KEMs without FO are completely broken under key reuse — the private key is recoverable after a few thousand samples (Fluhrer, 2016). ML-KEM has the needed properties. Raw ECDH does not formally meet IND-CCA2 as a KEM, but is safe for ephemeral TLS 1.3 use.
03 Negotiation: one pair, one code point

No new extension, no new grammar. Each specific combination is registered as a single NamedGroup and advertised in supported_groups like anything else. The identifier is opaque — no internal structure is implied or required — but it corresponds to an ordered tuple of two or more algorithms, and that order matters everywhere downstream.

RFC 9846 §4.2.8 — the structures being reused unchanged
struct {
    NamedGroup group;
    opaque key_exchange<1..2^16-1>;   // ← hybrid packs both algorithms in here
} KeyShareEntry;

struct {
    KeyShareEntry client_shares<0..2^16-1>;  // descending client preference
} KeyShareClientHello;

struct {
    KeyShareEntry server_share;                // server picks exactly one
} KeyShareServerHello;

Neither side sends lengths. Each parses the blob by fixed offsets known from the NamedGroup definition — the first n bytes are the traditional share, the rest is the KEM share. That is the entire framing story, and it is why fixed-length is a hard requirement rather than a convenience.
05 Wire format: direct concatenation

Values are concatenated directly — no additional encoding, no length fields, no delimiters. The client's blob holds public keys; the server's holds ciphertexts. For an (EC)DH component, the "public key" and "ciphertext" are both just the ephemeral key share.

Sizes are ML-KEM-768 (FIPS 203) and x25519, shown to make the shape concrete — RFC 9954 defines no algorithms itself, and the real component order is whatever the registered NamedGroup says, which is not always traditional-first.

TLS 1.3 requires every KeyShareEntry.key_exchange to be generated independently. Hybrid relaxes that in exactly one direction: the same algorithm may reuse its value across entries in the same ClientHello. Different algorithms must still be generated independently. Both of the following are legal for a client offering ECDH, PQ-only, and the hybrid pair:

Option A — fully independent
// three unrelated generations
MyECDHMyPQKEM.KeyGen() =
    (MyECDH.KeyGen(), MyPQKEM.KeyGen())

KeyShareClientHello {
  { 'MyECDH',        MyECDH.KeyGen()        },
  { 'MyPQKEM',       MyPQKEM.KeyGen()       },
  { 'MyECDHMyPQKEM', MyECDHMyPQKEM.KeyGen() },
}
Option B — reuse per component
ecdh  = MyECDH.KeyGen()
pqkem = MyPQKEM.KeyGen()
pair  = (ecdh, pqkem)   // same values, concatenated

KeyShareClientHello {
  { 'MyECDH',        ecdh  },
  { 'MyPQKEM',       pqkem },
  { 'MyECDHMyPQKEM', pair  },
}
06 Key schedule: one substitution

The second concatenation. ss1 || ss2 is inserted into the standard TLS 1.3 key schedule exactly where the (EC)DHE shared secret used to go. Nothing else in the schedule changes — no extra extract step, no new labels, no length fields in the concatenation.

FIPS angle
A hybrid often mixes an approved component (ECDH on nistp256/secp256r1) with an unapproved one (post-quantum). NIST SP 800-56Cr2 lists plain concatenation as an approved method for producing a hybrid shared secret when one of the constituent secrets comes from an approved method — which is a large part of why concatenation won over more elaborate combiners.
Why plain concatenation is sound
Under the assumption that each shared secret is fixed-length once the combination is fixed, this construction is the dual-PRF combiner of Bindel et al. (PQCrypto 2019), shown to preserve security provided the hash function is a dual-PRF. See also Giacon et al. on KEM combiners. The "secure if one component survives" property is a theorem here, not an assertion.

Tradeoff

Duplicated key shares

Because each combination carries its own copy of every component, offering two hybrids that share a component means sending that component twice. A client offering both SecP256r1MLKEM768 and X25519MLKEM768 sends two full ML-KEM-768 public keys — the "minimal duplicate information" goal loses here.

Pairing a hybrid with a plain traditional group for fallback costs almost nothing by comparison: the duplicated secp256r1 key is tiny.

Why fixed length is non-negotiable

Variable-length secrets fed to hash functions are dangerous in general. A longer secret can mean more internal blocks processed, which has produced real timing side channels — Lucky Thirteen and Raccoon are the cited precedents.

Aviram et al. add a second problem: variable-length secrets become risky if the KDF's hash function ever loses collision resistance. Concatenating variable-length values would need a length prefix or other unambiguous encoding to stay injective — a different mechanism than this document specifies.

09 Scope, registry, and prior art
Deliberately out of scope
Which next-generation algorithms to use, their identifiers, and their encodings — those belong to other documents. And authentication with next-generation algorithms: a quantum computer could retroactively decrypt recorded sessions, but it cannot retroactively break the authentication of a session that already happened. That asymmetry is why confidentiality is the urgent half. Out-of-band keying material is also out of scope — components are negotiated and transmitted inside the TLS 1.3 handshake.
IANA considerations

RFC 9954 is added as a reference for the TLS Supported Groups registry.

Hybrid combinations defined per this document get identifiers in a range distinct from the Finite Field Groups range. Registry columns: Recommended SHOULD be N, DTLS-OK SHOULD be Y.

Related work & prior attempts

Earlier drafts. TLS 1.2: Whyte et al. (QSH), Campagna & Crockett. TLS 1.3: Kiefer & Kwiatkowski (ECDHE-SIDH), Schanck & Stebila (additional key share extension), Whyte et al.

Prototypes. TLS 1.2: BCNS15, Google's CECPQ1, FrodoKEM, OQS-OpenSSL 1.0.2, AWS s2n. TLS 1.3: CECPQ2, OQS-OpenSSL 1.1.1, the OQS provider for OpenSSL 3. These were ad hoc — none implemented one of the drafts above.

Elsewhere in the IETF. RFC 9370 (multiple key exchanges in IKEv2), RFC 8784 (post-quantum preshared keys in IKEv2), RFC 8773 (external PSK with certificate auth in TLS), RFC 8391 (XMSS).

Academic lineage. Even & Goldreich started the study of combining symmetric schemes; Zhang, Dodis, and Harnik examined combining public key encryption; Harnik coined robust combiner for a compiler that builds a hybrid while preserving security properties. Giacon and Bindel extended this to KEMs — Bindel's dual-PRF combiner is the one this construction lands on.
