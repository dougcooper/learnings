01

The one-paragraph version

§1.2, §2

TLS 1.3 is not TLS 1.2 with better ciphers. It is a redesign that removes every mode which could be misused, and folds the key exchange into the very first message so the handshake finishes in one round trip instead of two.

The pivotal change: the client guesses. Instead of waiting for the server to announce which key-exchange group it supports, the client sends a Diffie-Hellman public key in its very first message. If it guessed a group the server accepts — which it almost always does — both sides can compute a shared secret immediately, and every message after the server's first reply is encrypted.

TLS 1.2 — two round trips

RTT 1: ClientHello → ServerHello + Certificate + ServerKeyExchange → ClientKeyExchange + ChangeCipherSpec + Finished.

RTT 2: server Finished, then application data. The certificate travels in the clear, and static-RSA key exchange means recording traffic today and stealing the server key later decrypts it.

cert in cleartext no forward secrecy (static RSA) MAC-then-encrypt

TLS 1.3 — one round trip

RTT 1: ClientHello with a key share → ServerHello with the matching share, then everything else encrypted: extensions, certificate, signature, Finished.

The client's reply carries its Finished and can be immediately followed by application data. Ephemeral (EC)DHE is the only key-exchange mechanism, so a stolen server key never decrypts past traffic.

cert encrypted forward secrecy always AEAD only

Forward secrecy, briefly

Each connection generates a throwaway Diffie-Hellman key pair and discards it afterwards. An attacker who records the encrypted traffic and later steals the server's long-term private key still cannot decrypt it — that key only signs, it never encrypts the session. TLS 1.2's static-RSA mode did not have this property; TLS 1.3 deleted the mode.

RFC 8446 §1.2 — "all public-key based key exchange mechanisms now provide forward secrecy"

The full handshake

§2, §4.1–4.4

Three phases, one round trip. Key exchange (unencrypted, by necessity), then server parameters and authentication (encrypted under handshake keys), then application data (encrypted under application keys).

The key schedule

§7.1

Every key TLS 1.3 ever uses comes out of one ladder. Secrets flow downward; each rung mixes in new input material and spurs off the traffic secrets for that stage.

Two primitives do all the work. HKDF-Extract takes messy input (a Diffie-Hellman result, a pre-shared key) and condenses it into a uniform secret. HKDF-Expand-Label takes that secret plus a short label and stretches it into as many distinct keys as needed — different labels give provably unrelated keys from the same parent.

PSK or all-zeroes if none
HKDF-Extract Early Secret

Exists only so resumption and 0-RTT have something to derive from. On a fresh connection with no pre-shared key, the input is a string of zero bytes and the outputs below go unused.

  • binder_keyProves the client really holds the PSK, not just a copied ticket ID
  • c e trafficEncrypts 0-RTT early data — not forward secret
  • e exp masterEarly exporter, for protocols layered on top of TLS

From traffic secret to actual keys

A traffic secret is not itself an encryption key. Each direction expands its secret twice:

write_key = HKDF-Expand-Label(S, "key", "", key_len)
write_iv  = HKDF-Expand-Label(S, "iv",  "", iv_len)

Ratcheting forward (KeyUpdate)

Long connections rotate keys without a new handshake:

secret_N+1 = HKDF-Expand-Label(secret_N, "traffic upd", "", Hash.len)

One-way — an attacker who compromises secret_N+1 cannot roll back to secret_N.

The record layer

§5.1–5.5

Every TLS 1.3 cipher suite is AEAD — authenticated encryption with associated data. One primitive both encrypts and authenticates in a single pass, which eliminates the entire class of MAC-then-encrypt padding-oracle bugs that plagued TLS 1.2 (BEAST, Lucky13, POODLE).

The record format also hides more than it used to. The real content type moves inside the encrypted blob, and the outer header always claims to be application_data — so an observer can't distinguish a handshake record from an alert from real traffic.

Per-record nonce (§5.3)

No nonce is transmitted. Each side keeps a 64-bit sequence counter, left-pads it with zeros to the IV length, and XORs it with the static write_iv from the key schedule. Same counter on both ends means both derive the same nonce without spending bytes on the wire.

The counter resets to zero whenever keys change, and it must never wrap — hence KeyUpdate.

Key usage limits (§5.5)

AEAD constructions degrade after enough records under one key. RFC 8446 gives concrete ceilings — for AES-GCM, roughly 224.5 records before a KeyUpdate is required. Exceeding them is a real cryptographic risk, not a formality.

The five cipher suites

TLS 1.3 cipher suites name only the AEAD and the hash. Key exchange and signature algorithm are negotiated separately by extension — so the combinatorial explosion of TLS 1.2 suite names is gone.

05

Resumption and 0-RTT

§2.2, §2.3, §4.6.1, §8

TLS 1.3 collapses session IDs and session tickets into a single mechanism: the pre-shared key. After a handshake completes, the server sends one or more NewSessionTicket messages; each ticket is a PSK identity the client can present later.

Resuming with a PSK and a fresh key share gives a normal 1-RTT handshake with forward secrecy restored. Resuming with the PSK alone allows the client to send application data in its very first flight — 0-RTT — with a real security cost attached.

§2.3 — 0-RTT: data rides along with the first flight, before the server has said anything

0-RTT data is replayable. This is by design, not a bug.

Early data is encrypted under a key derived only from the pre-shared key — nothing fresh from the server is mixed in yet. Two consequences follow. First, no forward secrecy: whoever later obtains the PSK can decrypt it. Second, an attacker who captures the early-data flight can replay it verbatim to the same server, or to a different server in the same cluster, and it will be accepted.

§8 — only send requests you would be comfortable having executed more than once. GET, not POST.

Single-use tickets

The server records each ticket and rejects the second use. Effective, but requires shared state across a server fleet.

ClientHello recording

Hash and store recent ClientHellos within a bounded time window; reject duplicates. Bounded memory, bounded window.

Freshness checks

obfuscated_ticket_age lets the server verify the client's reported elapsed time is plausible, narrowing the replay window.

The PSK binder

The pre_shared_key extension must be last in the ClientHello, because it carries an HMAC — the binder — computed over the ClientHello truncated right before the binder itself. This proves the client actually possesses the PSK rather than having merely copied a ticket identity from an observed connection.

What was deleted, and why

§1.2

The most consequential part of RFC 8446 is a list of subtractions. Nearly every major TLS attack of the 2010s traced back to a legacy mode kept for compatibility; TLS 1.3 removed the modes instead of hardening them.

Removed
Impact
Why
Static RSA key exchange
major
Encrypting the premaster secret to the server's long-term key means no forward secrecy — and it powered ROBOT and Bleichenbacher-style oracles. All key exchange is now ephemeral (EC)DHE.
Static Diffie-Hellman suites
major
Same forward-secrecy problem as static RSA.
Compression
major
Compressing before encrypting leaks plaintext through ciphertext length. This was CRIME.
Renegotiation
major
A long history of injection attacks. Replaced by narrowly-scoped post-handshake messages: KeyUpdate and post-handshake client auth.
Non-AEAD ciphers (CBC, RC4)
major
MAC-then-encrypt CBC produced BEAST, Lucky13 and POODLE. RC4 was simply broken. AEAD only, now.
Custom / arbitrary DHE groups
medium
Servers offering weak or malicious groups enabled Logjam. Only named, vetted groups remain.
RSA PKCS#1 v1.5 signatures
medium
Replaced by RSASSA-PSS, which has a proper security proof. (v1.5 remains permitted inside certificates for ecosystem reasons.)
DSA signatures, MD5 & SHA-1 in the handshake
medium
Obsolete and, in SHA-1's case, collision-vulnerable — SLOTH.
ChangeCipherSpec
minor
No longer meaningful — key changes are implied by message sequence. Survives only as an ignored dummy record for middlebox compatibility.
Session IDs & RFC 5077 tickets
minor
Two resumption mechanisms unified into one: PSK.
EC point format negotiation
minor
One format (uncompressed) is mandated. One less thing to negotiate wrongly.

Version negotiation moved, too

The legacy_version field in ClientHello is frozen at 0x0303 (TLS 1.2) forever, because middleboxes on the internet reject anything higher. Real version negotiation happens in the supported_versions extension. TLS 1.3 records also always claim to be TLS 1.2 on the wire — a deliberate disguise so deployed middleboxes let them through.

Downgrade protection

§4.1.3

An active attacker who can strip the supported_versions extension could try to force both sides down to TLS 1.2 and attack that instead. TLS 1.3 defends with a sentinel hidden in plain sight.

A TLS 1.3-capable server that ends up negotiating an older version must write a fixed byte string into the last 8 bytes of ServerHello.random:

§4.1.3 — downgrade sentinel values 
negotiating TLS 1.2:      44 4F 57 4E 47 52 44 01   // "DOWNGRD" + 0x01
negotiating TLS 1.1 or below: 44 4F 57 4E 47 52 44 00   // "DOWNGRD" + 0x00

A client that offered TLS 1.3 and sees this sentinel in a supposedly-1.2 response knows the downgrade was not the server's genuine choice, and aborts. Because ServerHello.random is covered by the TLS 1.2 Finished MAC, an attacker cannot strip the sentinel without breaking the handshake.

Why the transcript hash matters everywhere

Notice the recurring pattern: CertificateVerify signs the transcript, Finished MACs the transcript, and the Master Secret is derived from the transcript. Any modification an attacker makes to any handshake message — anywhere, at any point — produces a different hash, and the connection fails at the first check. That's the structural reason the handshake is tamper-evident as a whole rather than message by message.
