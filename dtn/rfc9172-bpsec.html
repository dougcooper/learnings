Bundle Protocol Security (BPSec)

BPSec adds data-integrity and confidentiality services to the Bundle Protocol (BPv7), the transport of Delay-Tolerant Networking (DTN). DTN links are intermittent, slow, asymmetric, and noisy — bundles may sit for days or years before delivery, so security must work without live contact with a central authority and must protect data at rest.

The two security services

BPSec defines exactly two services, each delivered as a Bundle extension block. There is deliberately no hop-by-hop authentication — "hop" is ambiguous in a BP overlay and adjacent nodes rarely share compatible security capability.

Integrity — Block Integrity Block

Detects changes to plaintext target data from processing errors, the environment, or intentional tampering.

  • Block type code 11 (BPv7)
  • Verifiable by any node from security source to destination
  • Context MUST use authentication or error-detection mechanism
  • Never used for ciphertext integrity coming out of a BCB
Confidentiality — Block Confidentiality Block

Makes target data unintelligible to unauthorized nodes by producing ciphertext plus authentication information.

  • Block type code 12 (BPv7)
  • Context MUST use AEAD (authenticated encryption with associated data)
  • Encryption is in-place: target's block-type-specific data becomes ciphertext
  • Also provides ciphertext integrity-protection mechanisms
Block-level granularity, not bundle-level. A single bundle holds blocks of different kinds — a primary routing block, payload, and extension annotations — with different protection needs. BPSec protects each block individually: a payload can be encrypted while a summary extension block is integrity-signed but left readable for waypoint access.

The Abstract Security Block (ASB)

BIB and BCB share one structure — the ASB — encoded in CBOR as the block-type-specific data. It is never instantiated directly; each block type wraps it. Targets are identified by block number.

1Security Targetsblock numbers this operation protects — ordered, no duplicatesCBOR array<uint>
2Security Context IdIANA-registered context implementing the algorithmsuint
3Security Context Flagsbit 0 (0x01) = "parameters present"; higher bits reserved → 0uint (bitfield)
4Security SourceEID of the node that added the operationCBOR array (EID)
5Security Context Parametersarray of (Id, Value) tuples — per-context, not globally uniqueoptional
6Security Resultsone entry per target, each an array of (Result Id, Value) tuplesCBOR array<array>

A single block may carry multiple operations when every target shares the same service type, context parameters, and source — common info is stated once, target-specific results stay individual. Uniqueness rule: a given service on a given target may appear only once per bundle. OP(bib-integrity, payload) twice is forbidden; the same service on two different targets is fine.

Canonical forms: what the cipher suite actually sees

Integrity and confidentiality only work if the security source, every verifier, and the acceptor all feed the identical byte sequence to the cipher suite. BPSec guarantees this with Deterministically Encoded CBOR (RFC 8949) canonical forms — the canonical encoding includes a field's own CBOR encoding but not any encapsulating CBOR framing around it.

The rules
  • Primary block canonicalized per RFC 9171 + Deterministic CBOR
  • Non-primary blocks canonicalized per RFC 9171 + Deterministic CBOR
  • Canonical form carries each field's CBOR encoding, not the framing around it
  • Reserved / unassigned processing-control flags must be set to 0 in canonical form
  • A security context MAY define its own canonicalization — it takes precedence

One field is special. Only the block-type-specific data field may be encrypted — everything else must stay readable for routing and processing, but may be bound into the integrity calculation as Additional Authenticated Data (AAD). That is exactly how a BCB protects the ciphertext's header fields without encrypting them.

Processing order: confidentiality first, then integrity

When BIBs and BCBs share a target, processing must be deterministic across every node. The rule is fixed: BCBs are evaluated before BIBs, and a BIB is never checked against ciphertext.

Three roles, not one: source, acceptor, verifier

BPSec splits "who touches a security operation" into three distinct roles. The flow above treats the acceptor as the terminator, but a node can also be a mere verifier — it checks integrity without removing the operation, so the protection survives onward to the real acceptor down the path.

RoleWhat it doesRemoves the op?
Security Source BP node that adds a security operation to the bundle. Recorded in the ASB's Security Source field. n/a — creates it
Security Acceptor Processes and terminates the operation (e.g. destination decrypts a BCB). Removes op-specific info; drops the block once all its ops are done. Yes
Security Verifier Non-acceptor that dispositions / checks an operation — e.g. verifies a BIB to avoid forwarding corrupt data. No (if it passes)
The verifier's non-removal rule. If a verifier's integrity check passes, it MUST NOT remove the operation before forwarding — the protection must live on to reach the acceptor. Only a failed check triggers policy-driven action. That is what lets integrity coverage span multiple hops without each intermediate hop stripping it.

Block interactions & ordering constraints

BIB and BCB can coexist, but their interactions are tightly constrained to keep the security model sound. The headline rule: for a given target, BIBs are added before BCBs.

Allowed
  • Same service, different targets
  • Different services, same target (BIB + BCB)
  • BCB targeting a BIB that shares its target
  • Waypoint removing then re-adding a block
Forbidden
  • BIB targeting a BCB
  • BCB targeting another BCB
  • BCB targeting the primary block
  • BCB targeting a BIB with different targets
  • Duplicate op on the same target
Must hold
  • BIB added before BCB for the same target
  • Adding a BCB over all a BIB's targets → encrypt that BIB too
  • Adding a BCB over some BIB targets → split the BIB
  • BCB over payload → set "replicate in every fragment"
Shortcut for source-side integrity + confidentiality. If you need both at the source, don't stack a separate BIB and BCB — use a single BCB whose context generates integrity results. This sidesteps the split/encrypt dance entirely.

Threat model: "Olive" the on-path attacker

BPSec scopes its threat model to on-path attackers (OPAs) per RFC 3552. "Olive" sits between source Alice and destination Bob and can receive, examine, modify, forward, and generate bundles. Three privilege tiers define what BPSec can and cannot stop.

The three Olive classes
ClassHoldsWhat BPSec can do
Unprivileged node Only public cryptographic material Low risk — confidentiality and integrity hold against this attacker.
Legitimate node Provisioned material K_M + public Medium risk — can replace Alice's BIB with its own signature. Mitigated by IND-CCA2 BCB covering BIB + data.
Privileged node K_M, K_A, and/or K_B High risk — tantamount to compromise; BPSec cannot detect or remove such an attacker.
Unprivileged — the outsider
Olive holds no keys. She can observe bundles in flight but cannot decrypt BCB-protected content, forge a valid BIB signature, or authenticate as a network member. Both confidentiality and integrity fully hold against her. Her only remaining lever is traffic analysis — who talks to whom, when, and how much — which no encryption stops.
Legitimate — the insider
Olive is a real network member with shared keying material K_M, so she can produce and verify valid operations. The core danger is signature substitution: she strips Alice's BIB and re-signs the block with her own valid key, so a forged bundle looks legitimate. She still can't read BCB-encrypted data unless she holds that specific key. Fix: an IND-CCA2 BCB that authenticates the BIB and the data together — any swap breaks the AEAD tag.
Privileged — the compromise
Olive holds an endpoint's own material — Alice's K_A or Bob's K_B. She can forge Alice's signatures, impersonate her, and decrypt anything bound for Bob. This is key compromise, not a protocol flaw: no cryptography can defend once the endpoint's own keys are stolen. The defense is operational — key rotation, HSMs, access control — outside BPSec's reach.
Attack behaviors → BPSec mitigations
AttackWhat Olive doesMitigationResidual
Eavesdropping Reads passing bundles; may retain them for years to cryptanalyze later BCB encryption. Long-lived bundles raise the cryptanalysis budget. Traffic analysis always possible
Modification Alters data, adds/removes/replaces blocks or signatures BIB + BCB integrity. Block removal needs out-of-band policy describing expected ops. Signature substitution by legitimate Olive
Topology Influences routing decisions BIB over primary block, encapsulation, or strategic primary-block manipulation. Routing policy is out of scope
Message injection Replays old bundles or injects new ones BCB w/ replay-resistant crypto; nonces, timestamps, Bundle Age block under BIB/BCB. Application must add uniqueness
Sharing one key set across all nodes collapses the tiers. If every node holds the same material, "legitimate" equals "privileged" — the medium-risk tier disappears and any node can forge any signature. BPSec explicitly recommends against provisioning this way.

Security contexts: the pluggable crypto layer

A security context is the bundle of algorithms, parameters, and results that actually implements a service. BPSec defines the framing; the context does the cryptography. No single context suits every network — resource-constrained vs. well-resourced differ — so contexts are registered and user-configurable. Mandatory-to-implement defaults live in RFC 9173.

What a context must define
  • Supported services (BIB, BCB, or both) per service
  • Parameter Ids, types, and encoding
  • Result Ids, types, and encoding
  • Own canonicalization if defaults don't suffice
  • Ciphertext-size statement (may exceed plaintext)
  • Block-header fields included in integrity (AAD)
DTN-specific design pressures
  • Data lifetime — bundles persist for years; algorithms must stay strong that long
  • One-way traffic — two-way handshakes may be impossible, limiting Diffie-Hellman
  • Opportunistic access — key-distribution centers are often impractical
Three example context types (RFC Table 1)
Key Exchange AES
Parameters carry an encrypted key + IV — the session key rides inside the bundle.
Pre-Shared Key AES
Only the IV travels as a parameter; the key is pre-provisioned out of band.
Out-of-Band AES
No parameters at all — key and IV are entirely configured out of band.

Other Security Blocks: the extension point

BIB and BCB are not the end of the story. BPSec permits Other Security Blocks (OSBs) — new block types that coexist with BIB/BCB — provided they follow rules that keep the deterministic processing model intact. This is how BPSec grows without a new base spec.

OSB coexistence requirements
  • MUST NOT reuse BIB/BCB type codes or enumerations
  • MUST state whether they can target — or be targeted by — BIB/BCB
  • MUST give a deterministic processing order that does not alter BIB/BCB ordering
  • MUST provide own canonicalization if defaults are insufficient
  • MUST NOT conflict with BPSec behavior requirements
  • MUST specify their fragmentation behavior
Why the strict rules. Determinism is BPSec's highest priority — every node must process a bundle's security blocks in the same order. An OSB that injected its own ordering, or reused a type code, would break that invariant. These requirements let the protocol extend without undoing the guarantee.

Security reason codes

Five BPv7 status-report reason codes (values 12–16) let nodes signal security outcomes. Policy should govern when these are sent — e.g. only to a verified report-to address, possibly encrypted, to avoid leaking operational detail.

CodeNameMeaning
12Missing security operationA required operation was absent from the bundle.
13Unknown security operationOperation not understood — e.g. unrecognized context Id.
14Unexpected security operationNode is neither verifier nor acceptor — not necessarily an error.
15Failed security operationProcessing failed for reasons other than misconfiguration.
16Conflicting security operationBPSec protocol violation from non-conformant operations.

What BPSec deliberately does not do

Out of scope. DTN infrastructure security, threats from sharing compute resources with BPSec software, fitness of specific cryptographic methods, security-policy implementation, and combination with other protocols. Key management is assumed to be handled entirely separately — BPSec defines no key strategy.
Fragmentation. Only payload blocks can be fragmented; security blocks cannot. BIBs/BCBs MUST NOT be added to bundles carrying the "fragment" flag, and confidentiality should be applied before any fragmentation.
