Bundle Protocol Version 7

BPv7 is a store-carry-forward overlay for Delay-Tolerant Networking — communications in stressed environments with intermittent connectivity, long delays, and high error rates. It sits above the application layer of whatever underlying networks happen to be available, decoupling end-to-end delivery from any single transport. This page unpacks the protocol’s node architecture, CBOR bundle structure, processing lifecycle, and control flags.

The Bundle Node

Every bundle node has three components: an Application Agent (AA) that produces/consumes data, a Bundle Protocol Agent (BPA) that runs the protocol, and one or more Convergence-Layer Adapters (CLAs) that map bundles onto underlying transport stacks. The AA’s administrative element also handles status reports and may even act as a CLA to enable bundle tunneling.

Bundle Structure on the Wire

A bundle is a CBOR indefinite-length array: exactly one primary block (block 0, immutable end-to-end), followed by one or more canonical blocks, exactly one of which is the payload block (block 1, always last), then a CBOR break stop code. Block numbers identify blocks and are unrelated to array order. The primary block carries 8–11 fields depending on fragment/CRC status.

Mandatory Extension Blocks

All implementations MUST recognize, parse, and act on these three extension blocks (they need not produce them). They track the bundle’s path, age, and hop budget.

Block type 6
Previous Node
Identifies the node that forwarded this bundle to the local node. Source bundles MUST NOT contain it; others SHOULD contain exactly one. The BPA rewrites it at each forwarding hop.
Block type 7
Bundle Age
Milliseconds elapsed between creation and most recent forwarding. MUST be present (exactly one) when creation time = 0; otherwise at most one. Drives expiration when clocks are unreliable.
Block type 10
Hop Count
Array [hop limit, hop count]. Limit is 1–255 (stable after creation); count starts at 0 and increments per hop. Exceeding the limit triggers deletion with reason Hop limit exceeded.

Every endpoint ID is a URI scheme:ssp encoded as a CBOR array [scheme-code, ssp]. Two schemes are defined: dtn (with a ~-prefixed demux marking non-singleton endpoints) and ipn (always singleton, numeric node/service). 07

Security Posture

BPv7 deliberately splits security out to BPSec (RFC 9172), which adds Block Integrity Blocks (BIBs) for integrity and Block Confidentiality Blocks for secrecy. The base protocol itself does not guarantee delivery — that is a convergence-layer and extension concern.

Integrity. A primary block may carry CRC type = 0 only when a BPSec BIB targets it. Verifying BIB signatures that target the primary block is required for reliable, consistent endpoint identities.
Identity spoofing. Malicious URI construction can declare false sources or steer bundles to harmful endpoints. Schemes must be validated before trust is extended.
Traffic analysis. Endpoint IDs are visible at the convergence layer and leak metadata. Use secure CL protocols that do not expose EIDs, and remember BP itself never assures delivery — reliable CLs reduce loss, but end-to-end assurance needs extensions.
08

BP as an Overlay Network

BP does not replace the networks it crosses — it overlays them. Applications talk to the Bundle Protocol Agent; the BPA hands bundles to convergence-layer adapters, which map them onto whatever transport/network stacks happen to be reachable. End-to-end delivery may hop across several heterogeneous networks, exploiting scheduled, predicted, or opportunistic contacts. Late binding lets an overlay endpoint ID resolve to a concrete network address only when a contact actually appears.

Convergence-Layer Services

The convergence layer is a thin shim between BP and an integrated protocol stack. The spec does not define any single CL protocol; it defines the services the CLA must provide so the BPA can send and receive bundles. A CL protocol may simply multiplex/demultiplex bundles, or offer extra functionality (reliability, framing, session management).

  • →

  • ·

Reliability is not end-to-end. A reliable CL reduces loss on one hop, but BP itself never guarantees delivery — a bundle may still expire, be deleted, or never reach a contact. End-to-end assurance is the job of higher-layer extensions, not the convergence layer.

Identifiers, Time & Timestamps

Two data types pin a bundle to a moment and a sender. DTN time is a monotonic millisecond count; the creation timestamp pairs it with a sequence number so that source node ID + creation timestamp uniquely identifies a single transmission even when two bundles are created in the same millisecond.

4.2.6 · CBOR unsigned integer
DTN Time
Not affected by leap seconds.
  • ·
    Epoch
    2000-01-01 00:00:00 UTC — milliseconds elapsed since then
  • ·
    Zero
    Means “time unknown” — used when the node has no accurate clock
  • ·
    Leap-seconds
    Ignored — the count is a pure elapsed-time integer, not a civil clock
4.2.7 · CBOR array of 2
Creation Timestamp
Identifies one transmission.
  • 1
    Bundle creation time
    DTN time at which the transmission request was received
  • 2
    Sequence number
    Monotonically increasing positive counter; MAY reset when current time advances by 1 ms
  • ·
    No-clock fallback
    Creation time set to 0; sequence counter never resets — ordering still unique

The Bundle Age extension block (type 7) complements this for nodes without clocks: when creation time is zero, age is the only way to judge expiration, which is why the block is then mandatory.

Registration & Delivery Semantics

A node joins an endpoint by holding a registration — a small state machine with Active and Passive states and an associated delivery-failure action. Delivery happens only when the destination endpoint has a matching registration and the bundle has not already been delivered or abandoned.

Fragmentation & Reassembly

Unless the “must not be fragmented” flag is set, any node may split a bundle into two fragments whose payloads are the first N and last M−N bytes of the original (0 < N < M). Fragments are themselves bundles and may be fragmented again. Reassembly reconstructs the original ADU from non-overlapping material extents, and may happen at the destination or at any intermediate node.

5.8 · fragmentation rules
When splitting a bundle
  • ·
    Payload split
    Concatenation of fragment payloads must equal the original payload
  • ·
    Primary block
    Set fragment flag; carry fragment offset + total ADU length; recompute CRC
  • ·
    Replicate flag
    Extension blocks flagged “replicate in every fragment” MUST appear in all fragments
  • ·
    Offset-zero rule
    For an offset-zero fragment from a non-fragment, ALL extension blocks are replicated
5.9 · reassembly
Reconstructing the ADU
  • ·
    Match key
    Fragments sharing source node ID + creation timestamp belong together
  • ·
    Material extents
    Non-overlapping continuous byte runs not already received
  • ·
    Completion
    When extents form a continuous array of length M, the ADU replaces the offset-zero fragment’s payload
  • ·
    Cleanup
    Drop “Reassembly pending” from the other matching fragments

Administrative Records

Only one administrative record type is defined: type 1, the bundle status report. Each record is a CBOR array of two items — a type code and the record content. Status reports travel as ordinary bundles with the “ADU is an administrative record” flag set.

Status report structure
  • 1
    Status information

  • 2

5.1 / 6.2 · generation rules
When and how reports are made
  • ·
    Off by default
    Status-report generation MUST be disabled unless explicitly enabled
  • ·
    Amplification bound
    One bundle can yield up to 1 + 2·(N−1) report bundles along an N-hop path
  • ·
    Admin-flag zeroing
    If the admin flag is set, all status-report-request flags MUST be zero
  • ·
    Block-flag zeroing
    In admin/anonymous bundles, “report on unprocessable block” MUST be zero in every block

IANA Registries

RFC 9171 establishes eight registries under the “Bundle Protocol” registry group. They gate extensibility: new block types, flag bits, reason codes, and URI schemes are all added through these registries rather than by amending the protocol. Block type codes 192–255 are reserved for private/experimental use and need no registration.
