How to Compare Bandwidth-Constrained Two-Party Secure Messaging Protocols

Auerbach (PQShield) · Dodis (NYU) · Jost (Blanqet) · Katsumata (PQShield / AIST) · Schmidt (Signal)
IACR Cryptology ePrint Archive · 2025 · eprint.iacr.org/2025/2267
The problem. Post-quantum key-agreement messages are 71× larger than Diffie-Hellman (≈ 2272 B vs 32 B). The Double Ratchet model that worked for DH no longer fits when each "CKA message" dwarfs the chat budget. Existing protocols (Apple PQ3, the recent Triple Ratchet) hide this with amortization or chunking — but there's no honest way to compare them on post-compromise security. This paper proposes a metric, an abstraction (Sparse CKA), and three new protocols — and proves no single protocol is universally best.

01Why this matters

Every modern messenger (Signal, WhatsApp, iMessage, Google RCS) achieves two security properties that ordinary encryption cannot:

Forward Secrecy (FS)
Past messages stay safe even if today's key leaks. Achieved trivially with a stream cipher and a fresh key per message.
Post-Compromise Security (PCS)
After a compromise, the protocol "heals" — within a bounded window, future messages are safe again. Requires interaction and public-key crypto. This is the expensive part.
The PCS bottleneck. In the pre-quantum world, PCS came from a Continuous Key Agreement (CKA) layer — in the Double Ratchet, that's a single 32-byte Diffie-Hellman group element per message. Post-quantum, a MLKEM-based CKA would cost 1088 + 1184 = 2272 B per message — over 70× larger. Signal's budget for the entire PQ overhead is 40 B. The mismatch is the entire problem.

02The conceptual problem: epochs ≠ messages

PCS is traditionally measured in epochs — defined as a change in communication direction. With unlimited bandwidth, an "epoch" = one CKA message = one fresh key, and the layers line up cleanly. The old way of comparing protocols is just: look at the underlying CKA.

Once bandwidth is limited, that breaks. Chunking splits one CKA message across many small messages. "Epochs" lose their meaning — a receiver may need dozens of messages before producing a single fresh key. Worse: in a balanced chat, half of the messages the receiver sends during a chunking exchange contain no new CKA material at all. From the CKA's point of view, those messages are wasted.

Figure. When chunking splits a single CKA message into many small pieces, half the bandwidth of a balanced conversation carries no PCS-relevant material. The old "count epochs" metric hides this.

03The fix: Sparse CKA (SCKA)

The new abstraction

The authors generalize CKA. In regular CKA, every outgoing message produces a fresh key. In SCKA, the protocol may output (t, I) = (⊥, ⊥) — meaning "no key this round, still collecting chunks." A key is only emitted when the SCKA is genuinely ready. This lets the abstraction cover:

  • Chunking — keys arrive after many small messages, not one big one.
  • Unidirectional key generation — only one party emits a key per round (halves the bandwidth cost).
  • Opportunistic sending — the receiver starts sending its response chunks while still receiving the initiator's chunks, instead of waiting for completion.

The SCKA interface is otherwise identical to CKA — the authors prove a generic SCKA → SM compiler that preserves bandwidth, so any SCKA drops into a Double Ratchet–style messenger with minimal glue.

Old way

CKA outputs a key every message. Epoch = message. PCS measured in epochs, which equals messages in practice. Breaks once bandwidth < native CKA size.

New way (SCKA)

SCKA outputs (t, I) only when ready. An "epoch" may span many messages. Security is still epoch-based but the SM layer knows which epochs are safe to use. The exposed set is tracked per-state as st.vuln.

Key insight. The authors replace the old ΔFS / ΔPCS numbers with a richer notion: a vulnerable message set attached to each state. This makes security analysis protocol-specific — exactly what's needed when you can't assume one-message-per-epoch anymore.

04Three new SCKA protocols

All three use chunking + erasure codes. They differ in what gets sent and when.

Opp-UniKEM-CKA · §4.1

One-shot, unidirectional

Alice generates a fresh MLKEM key pair, sends ek_A chunk-by-chunk. Bob responds with a ciphertext ct_B chunk-by-chunk. Roles reverse next epoch. Simplest baseline.

Opp-BiKEM-CKA · §4.2

Bidirectional KEM exchange

Each round, both parties send a chunk of their encapsulation key. No ciphertext is sent in the first phase — the ct arrives only after the ek has propagated. Key is recovered on receipt.

Opp-RKEM-CKA · §4.3

Ratcheting KEM (advanced)

Uses a Ratcheting KEM [Dodis et al. '24] — the chunk of ciphertext can itself be the encapsulation key for the next epoch. Reuses the same ~2272 B payload across epochs. Smallest per-epoch bandwidth.

The "opportunistic" trick in all three

Picture: Alice sends a long α, Bob replies with β = (β₀, β₁) where β₀ doesn't depend on α. With chunking, the naive order is: Alice finishes α → Bob decodes → Bob sends β. Opportunistic sending flips it: Bob starts streaming β₀ while still receiving α. In a balanced conversation, this overlaps the two flows and effectively halves the latency of a full CKA exchange. The CKA syntax cannot express this — you need SCKA, where the key output is decoupled from the message output.

05How to compare them (the framework)

For each candidate SM protocol and a given communication pattern (how often each side speaks, message sizes, drops), the framework computes the vulnerable message set over time after a synthetic compromise event. 06What the experiments show

No protocol wins everywhere. The "best" protocol depends on the communication scenario. This is the paper's headline result.

Balanced conversations (primary device)

Both sides send at similar rates. Opp-RKEM-CKA and protocols with opportunistic sending pull ahead — overlapping the inbound and outbound chunk flows roughly halves the effective healing latency.

Unbalanced (linked device, mostly receiving)

The receiver has few chances to send its own chunks back. UniKEM variants — which only need one party to ship a key — degrade more gracefully here than BiKEM, which waits for the other side.

Strict bandwidth cap (≤ 40 B / message)

Chunking-based protocols all behave similarly; the bottleneck is how many round trips a full CKA needs, not the chunking itself. Healing time ≈ (#chunks per side) / (bandwidth).

Robustness across patterns

Ratcheting-KEM and unidirectional variants show the most consistent performance across every pattern tested. They don't win every benchmark, but they're never the worst.

08Why this is a real contribution

1. A metric that actually works under bandwidth constraints

Vulnerable message sets replace ΔFS/ΔPCS. It makes the "how many messages get exposed" question precise even when CKA and message boundaries no longer align.

2. A new abstraction: Sparse CKA

Generalizes CKA so that keys need not arrive every message. This is the smallest change to the CKA model that captures chunking, unidirectional keys, and opportunistic sending — and it still compiles to SM with a near-identical construction to the original Alwen–Coretti–Dodis compiler.

3. Three concrete new protocols

Opp-UniKEM, Opp-BiKEM, and Opp-RKEM. They are the first SCKA protocols to make opportunistic sending a primitive, and they all enjoy generic instantiations from standard PQ KEMs (or RKEM).

4. An experimental framework

Models real Signal user behavior (primary device vs. linked device), runs all protocols under matched bandwidth, and produces comparable healing curves. Built in collaboration with Signal Messenger.

09Open questions and limitations

Not addressed
  • Resilience to state loss (cf. Cremers et al. on Signal's session handling) — the paper assumes clean state.
  • Multi-device / group messaging — two-party model only.
  • Fine-grained partial-state leakage (Blazy et al. taxonomy).
Implications for practice
  • PQ3's amortization trick (full CKA every 50 messages) is a different point in the trade-off space, not a strictly worse one — it wins where bandwidth is plentiful.
  • Chunking + opportunistic sending is the new Pareto frontier for low-bandwidth regimes.
  • For Signal specifically, the framework gives a way to test future proposals before deploying them.
The bottom line. Post-quantum secure messaging is not a single protocol problem — it's a family of trade-offs between per-message overhead, healing latency, and resilience to different communication patterns. This paper finally gives the field a metric, an abstraction, a small protocol zoo, and a measurement framework to make those trade-offs explicit. The "no optimal protocol" result is itself the contribution: it tells the field to stop looking for one and start choosing intentionally.

10Glossary

CKA
Continuous Key Agreement. The abstract protocol that runs "next to" encryption and produces fresh keys. Used by Double Ratchet.
SCKA
Sparse CKA. The paper's new abstraction. Same interface as CKA but may output ⊥ for "no key this round."
KEM
Key Encapsulation Mechanism. The post-quantum analogue of Diffie-Hellman. MLKEM (Kyber) is the standard one.
RKEM
Ratcheting KEM. A KEM where part of the ciphertext can be the next epoch's encapsulation key. Saves bandwidth.
FS / PCS
Forward Secrecy / Post-Compromise Security. The two key guarantees of a modern messenger. PCS is the expensive one.
Epoch
A round of the CKA / a change of communication direction. Under chunking, an epoch can span many messages.
Chunking
Splitting one large CKA message into many small chunks via erasure codes. Keeps per-message overhead low.
Opp. Sending
Receiver starts sending its chunks while still receiving the sender's. Overlaps the two flows. Needs SCKA to express.
