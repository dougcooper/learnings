Messaging Layer Security (MLS)

A tree-based group key agreement protocol. It lets two to thousands of members share an encryption key asynchronously — nobody has to be online at the same time — while delivering forward secrecy and post-compromise security at a cost that scales logarithmically, not quadratically, with group size.

2Actors & Trust Model

MLS deliberately splits the infrastructure into a trusted part (the Authentication Service) and an untrusted part (the Delivery Service). Confidentiality and integrity hold even if the Delivery Service is fully compromised — it only ever routes opaque ciphertext.

Client / Member

Holds the keys

An agent holding cryptographic keys that uses MLS to establish shared state with other clients. Each member occupies one LeafNode in the ratchet tree and owns a signature key, an HPKE encryption key, and a credential.

Group

The shared secret

A logical collection of clients sharing a common secret in a given epoch. The group advances through numbered epochs; every Commit creates a new epoch with a fresh key.

Authentication Service (AS)

Trusted · vouches for identity

Validates members' credentials at key protocol events. The AS binds an identity to a signing key (via basic credentials or X.509 chains). This is the one component MLS relies on for authenticity.

Delivery Service (DS)

Untrusted · routes messages

Stores and forwards MLS messages between members, and holds a directory of published KeyPackages. MLS is engineered so a malicious DS still cannot read content, forge members, or break group consistency.

3The Ratchet Tree

The heart of MLS. A perfect binary tree of height d with 2d leaves — one per member. Leaves hold member keys; every parent node holds an HPKE public key whose private key is known only to the members in its subtree. This is the tree invariant, and it is what makes a key update cost O(log n) instead of O(n).

To update its key, member A posts fresh HPKE public keys along its direct path (A, P01, Root) and encrypts the new path secret separately to the resolution of each copath node (B, then {C, D}). That is the key-encapsulation step pictured below — the whole reason MLS is logarithmic.

Path-secret encryptions to copath resolutions

Each recipient decrypts exactly one blob to recover a path secret, then derives the rest of its own ancestors' keys from it. The committer performs log₂ n encryptions; every member performs log₂ n derivations. Nobody's work touches O(n).

LeafNode · §7.2

Per-member signed data

Carries encryption_key, signature_key, credential, capabilities, extensions, and a self-signature over LeafNodeTBS. Its leaf_node_source says whether it came from a KeyPackage, an Update, or a Commit.

ParentNode · §7.1

Interior HPKE key holder

Holds encryption_key, parent_hash, and unmerged_leaves — leaves that were added after this node's key was generated and so don't yet know its private key.

Resolution · §4.1.1

Encrypting to a subtree

For a copath node, the ordered list of non-blank descendants you encrypt to. Lets a committer reach every member in a subtree without knowing interior private keys.

Tree & parent hashes · §7.8–7.9

Integrity of structure

Every node has a tree hash summarizing its subtree; parent hashes link a child to its parent. Together they bind the whole tree into the GroupContext so the DS can't quietly swap members or nodes.

How each operation mutates the tree (§12.3):

Add · §12.1.1

Insert a leaf

The newcomer's LeafNode (from its KeyPackage) goes into a free or blank leaf. Until the committer refreshes ancestors, that leaf is unmerged — it doesn't know its ancestors' private keys. A Welcome carries the path secrets it needs.

Update · §12.1.2

Refresh a leaf + path

A member replaces its own leaf key and regenerates keys up its direct path (the UpdatePath). Everyone who held the old keys is excluded from the new secrets — this is the PCS move.

Remove · §12.1.3

Blank a leaf

The evicted member's leaf is blanked. The committer then refreshes its own direct path so the removed member's old keys can't derive the new epoch's secrets.

Tree invariant (§4.2): a member knows a node's private key only if that node's subtree contains the member's leaf. Break the invariant and you lose confidentiality; MLS enforces it on every Commit, and the tree/parent hashes make any tampering detectable.
4Commit Mechanics

A Commit is the single atomic operation that changes group state. It does not merely list proposals — it physically rewrites the tree and advances the epoch. Two sides to it: building (what the committer does) and processing (what every other member does to arrive at the identical state).

Building a Commit · §12.4

The committer's side

  1. Resolve proposals — gather the referenced proposals from the pending list; validate they're combinable.
  2. Apply proposals to a provisional tree (§12.3): Add inserts leaves, Remove blanks leaves, Update replaces leaves; ExternalInit blanks the committer's leaf.
  3. Build the UpdatePath along the committer's filtered direct path — fresh HPKE keypair per node, a path secret chained leaf → root, each secret encrypted to the resolution of the matching copath node.
  4. Compute tree & parent hashes for the modified tree → the tree commit hash.
  5. Run the key schedule: init_secret(N) + confirmed transcript + tree commit hash → epoch_secret(N+1).
  6. Sign AuthenticatedContent; compute confirmation_tag = MAC(confirmation_key, confirmed_transcript_hash).
  7. For Adds, build a Welcome encrypting GroupInfo + the new epoch's group secrets to each invitee's KeyPackage HPKE key.
Processing a Commit · §12.4.2

Everyone else's side

  1. Validate the Commit's proposals and the committer's authorization to make them.
  2. Apply the same proposals to reproduce the identical provisional tree.
  3. Decrypt one path secret: find the copath node whose resolution contains you, decrypt that single blob, then derive the rest of your direct-path keys.
  4. Run the key schedule to derive epoch_secret(N+1) and its children.
  5. Verify the confirmation_tag matches → you and the committer hold the same state.
  6. On Adds, newcomers process the Welcome instead: decrypt group secrets with their KeyPackage private key, install the public tree + path secrets, and land in the same epoch.
Welcome & GroupSecrets · §12.4.3

How a newcomer reconstructs the tree

A Welcome carries the public GroupInfo (full tree + GroupContext) plus, per invitee, an encrypted GroupSecrets blob. GroupSecrets contains the path secret the joiner needs for its leaf's direct path — so with only their KeyPackage private key, a new member derives every key it's entitled to know and arrives at the epoch without anyone having sent it per-member ciphertext.

5Key Schedule & Epochs

A single chain derives every secret for one epoch, then feeds the next. Each Commit advances the group by one epoch: the committer runs the key schedule, and every member re-derives the same epoch secret from the updated tree. Every derivation uses a labeled HKDF (HKDF-Expand-Label, §5.1) with the domain string "MLS 1.0 ..." so epoch secrets, secret-tree keys, and message keys never collide across contexts.

Secret Tree · §9

Per-sender keys

encryption_secret seeds a tree that derives a separate key ratchet for each member, split into handshake and application traffic. Keys are deleted after use → forward secrecy.

Confirmation tag · §6.1

Same state, guaranteed

Every Commit carries a MAC over the confirmed transcript hash using confirmation_key. All members verify it → they arrived at the identical group state.

resumption_secret · §8.4

Linking epochs

Feeds ReInit (new params, same members) and subgroup branching as a pre-shared key, so a new group inherits the old group's security history.

Transcript hashes · §8.2

Confirmed vs interim

Confirmed covers proposals + commits up to and including this Commit; the key schedule mixes it in and the confirmation tag covers it. Interim also includes proposals received but not yet committed — it seeds the next epoch's pending set.

HKDF-Expand-Label · §5.1

Domain separation

Every derivation is HKDF-Expand-Label(secret, label, context, length) with the fixed "MLS 1.0 ..." prefix. Tree, handshake, and application contexts get distinct labels, so a key from one can't be mistaken for another.

GroupContext · §8.1

Shared public state

The digest members sign into every message: protocol version, cipher suite, group_id, epoch, tree hash, confirmed transcript hash, extensions. A signature is therefore group- and epoch-bound — useless if replayed elsewhere.

6Secret Tree & Per-Message Keys

Once an epoch has an encryption_secret, it seeds a Secret Tree (§9) that mirrors the ratchet tree but derives per-sender keys. Each member's leaf fans out into two ratchets — handshake and application — advanced one generation at a time. The per-message key and nonce come from HKDF; a reuse_guard prevents nonce reuse even if state is lost.

Secret Tree for sender A — same structure repeats for every member's leaf.
Generations · §9

One (key, nonce) per message

Each ratchet advances by generation. The sender claims the next free generation; the key and nonce are HKDF-Expand-Label of the ratchet secret tagged with the generation number. The receiver tracks each peer's generation counter to stay in sync.

reuse_guard · §6.3.1

Defense against nonce reuse

Four random bytes per PrivateMessage, XORed with the key-schedule nonce. If a bug or state loss ever produces the same nonce twice, the guard still makes the effective nonce differ — averting the catastrophic reuse of an AEAD keystream.

Sender-data encryption · §6.3

Who sent it, hidden

The sender's leaf_index, generation, and reuse_guard are encrypted (not sent in the clear) using a key derived from sender_data_secret and a ciphertext sample — so the DS can't even see which member authored a message.

Forward secrecy · §9.2

Delete on use

Once a generation's key is consumed and the receiver advances past it, the key is erased. A later compromise of member state cannot recover old message keys — that is forward secrecy at the message level.

7Protocol Lifecycle

Membership changes are proposals; only a Commit enacts them (the mechanics are in §4). Any member can commit. New members arrive via a Welcome encrypted to their KeyPackage's HPKE key; outsiders can also join through an external Commit built from a published GroupInfo — no existing-member help needed.

8Group Evolution: External Join, ReInit, Branching

Beyond the ordinary add/update/remove cycle, MLS defines three group-to-group transitions. All three are linked by the resumption_secret (§8.4), so the new group's first epoch is authenticated by — and inherits the security history of — the group it came from.

External Commit · §3.3, §12.4.3.2

Join with no Welcomer

An outsider joins without any existing member issuing a Welcome. The group publishes a GroupInfo carrying external_pub — an HPKE public key for external init. The joiner builds an ExternalInit proposal + Commit, contributing fresh key material through that path.

Use case: open/semi-open groups, asynchronous joins where no member is online to Welcome you.

ReInit · §3.4, §11.2

Same members, new params

Closes the current group and creates a new one with the same members but different parameters — e.g. a stronger cipher suite. A resumption PSK seeds the new group's first epoch, so it is authenticated by the old group's resumption_secret.

Subgroup Branching · §3.4, §11.3

Subset of members

Creates a new group containing a subset of the current members, again linked via a resumption PSK. The side group inherits the parent's security history without exposing the parent's future traffic.

Use case: side conversations, privilege tiers, breakout sessions.

The old group's resumption_secret seeds the new group's first epoch in both transitions.
Why the PSK link matters: a fresh group started from nothing has no authentication of its membership. Deriving epoch 0 from the parent's resumption_secret means only someone who was in the parent group could have produced it — the new group inherits the parent's trust, not just its members.
9Message Framing

Everything on the wire is an MLSMessage discriminated by wire_format (§6). Handshake traffic is usually a PublicMessage (signed, optionally MAC-tagged for membership); application traffic is a PrivateMessage (signed and encrypted). Inner content is one of three types: application, proposal, or commit.

AuthenticatedContent (§6.1) is the inner core: FramedContent + FramedContentAuthData (signature, and for Commits a confirmation_tag). The signature covers FramedContentTBS — which includes the wire format, the content, and (for members) the GroupContext — so a signature is meaningless outside its specific group and epoch.

10Security Properties

MLS is specified to deliver concrete guarantees against realistic adversaries — including one who controls the Delivery Service. Two headline goals: forward secrecy (past stays secret after a break-in) and post-compromise security (future heals after a break-in).

Forward Secrecy · §16.6

Past stays secret

Per-message keys are deleted after use, and every Commit rolls the epoch secret forward. Compromise of current state cannot decrypt old messages.

Post-Compromise Security · §16.6

Future heals

After a compromised member Updates its leaf key and someone Commits, the attacker is locked out of future epochs — they can't derive the new tree secrets.

Authentication · §16.5

Who said it

Credentials, validated by the AS, bind members to signing keys. Every message signature is bound to the GroupContext, so it can't be replayed across groups or epochs.

Group Consistency · §6.1, §8.7

Same state, all members

The confirmation tag and transcript hashes force every member to land on the identical group state after a Commit — a divergent DS cannot split the group's view.

DS-Resistance · §16.2–16.4

Dumb pipe

Content, sender data, and group metadata stay confidential and integral even if the DS is malicious — it only routes ciphertext and checks it cannot forge.

Uniqueness · §7.3, §16.7

No key reuse

Signature and encryption keys must be unique among members; KeyPackages shouldn't be reused (§16.8) to stop replay of stale join material.

11Primitives & Extensibility

Every MLS session runs on a single cipher suite (§5.1) — one HPKE (KEM + KDF + AEAD), one hash, one MAC, one signature. Operations are domain-separated with labeled constructions (SignWithLabel, EncryptWithLabel), and identifiers are hash-based (RefHash) so messages reference objects by digest.

Cipher suite · §5.1

One bundle per session

HPKE parameters (KEM, KDF, AEAD) + hash + MAC + signature algorithm. The seven registered suites (below) pair a curve KEM with a matching AEAD and signature; all use HKDF as the KDF.

Credentials · §5.3

Identity binding

basic — a bare identity assertion. x509 — a DER certificate chain whose end-entity key matches the leaf's signature_key. The AS validates these; expiry/revocation are operational (§5.3.2). An optional application_id extension is not authenticated (§5.3.3).

HPKE · RFC 9180

The workhorse

All public-key encryption in MLS — tree updates, Welcome encryption, sender-data encryption — uses HPKE. Its labeled API keeps tree, handshake, and application contexts cryptographically separated.

GREASE · §13.5

Forward compatibility

Senders sprinkle in random values (unknown cipher suites, proposal types, extensions) that receivers must ignore. Keeps old clients working as the protocol grows — extensibility is a first-class goal (§13).

12Putting It Together: One Epoch, End to End

A single epoch's life, traced through everything above. Members A, B, C share epoch N. Application traffic flows; then a member posts an Update for post-compromise security; a Commit advances to epoch N+1 and the secret tree resets. Every arrow the DS carries is opaque ciphertext.

The application message

§9, §6.3

A's PrivateMessage is signed, then encrypted with a key from A's application ratchet at generation 0. The generation + reuse_guard ride in the encrypted sender data, so the DS can't even tell who sent it.

The Update

§12.1.2

C posts an Update proposal. Proposals are inert — no secret moves until a Commit references them. Posting the proposal costs one signed, unencrypted PublicMessage.

The Commit

§12.4 → §8

A's Commit applies C's Update, rebuilds A's direct path (the UpdatePath), encrypts log₂ n path secrets, and runs the key schedule into epoch N+1. The confirmation_tag proves every member landed on the same state.

What changed across the epoch boundary: the epoch secret, the entire secret tree, and every per-sender generation counter all reset. A message from epoch N cannot be decrypted with epoch N+1 state and vice versa — that boundary is what gives MLS forward secrecy and post-compromise security at once.
