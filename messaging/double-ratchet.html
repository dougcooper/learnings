The Double Ratchet Algorithm

The Double Ratchet is the algorithm Signal uses to encrypt every message in a session. It combines a symmetric-key ratchet (a chain of keys derived from the previous one, so each message gets its own key) with a Diffie-Hellman ratchet (a new key agreement each time someone replies, so past messages stay secret even if a key leaks later). Together they give forward secrecy (past messages stay sealed) and post-compromise security (a fresh key agreement heals the channel after a leak).

The symmetric-key ratchet (per-message keys)

A chain key (CK) is a single secret that evolves step by step. Each step turns the current CK into a new CK and spits out a fresh message key (MK). MK encrypts one message; CK feeds the next step. The maths is one-way: a leaked MK can't recover CK, and a leaked CK can't recover past MKs.

KDF_CK — the chain step
// Each call advances the chain by one message function KDF_CK(ck): const (new_ck, mk) = HMAC(ck, 0x02) return (new_ck, mk) // mk → message key (32 bytes) — encrypts one message // ck → new chain key — feeds the next step
Sending chain
Alice's CKs. Each time she sends, she steps it forward and gets the next MK. After sending 10 messages she's had 10 distinct MKs from one initial CK.
Receiving chain
Bob's CKr. Same algorithm, but he uses it to decrypt. He must land on the same MKs Alice produced, which means both sides need the same starting CK (derived from a shared DH).
Why one-way?
HMAC is a one-way function. Knowing MK_n doesn't let an attacker find CK_{n+1}, so past message keys remain secret even if a current key leaks.
Try to compute, then read on. KDF_CK is the only KDF called per message. The DH ratchet below only fires when the conversation direction flips — so the CPU cost of "encrypt one message" is dominated by HMAC, not by Diffie-Hellman.
03

The DH ratchet (a fresh key agreement per turn)

Every time the conversation direction flips (Alice replies, then Bob replies), both parties generate a new DH key pair, exchange public keys, and mix the resulting shared secret into a new root key (RK). This RK seeds a fresh chain — so even a long-lived attacker who has captured all previous DH outputs can't decrypt future messages.

KDF_RK — the DH step
// Triggered when a new DH ratchet public key arrives function KDF_RK(rk, dh_out): // dh_out = DH(my_DH_priv, their_DH_pub) — ECDH shared secret const (new_rk, ck) = HMAC(rk, dh_out) return (new_rk, ck) // new_rk → next root key (will feed the next DH step) // ck → first chain key of the new chain
State variables
  • DHs, DHr — our and their current DH key pairs
  • RK — root key, one per DH ratchet step
  • CKs, CKr — current chain keys
  • Ns, Nr — message counters per chain
  • PN — length of the previous sending chain (for header decryption)
  • MKSKIPPED — map of skipped message keys for out-of-order delivery
Post-compromise security

The whole point of the DH ratchet: if an attacker once got hold of the current state (a phone was compromised, for example), the next round of DH exchanges produces keys they don't have. The channel "heals" itself on the next reply.

04

Header encryption (Section 4)

The Double Ratchet encrypts the payload — but the header (which DH key and which message counter) leaks metadata. The header itself gets encrypted with a per-message header key so that an eavesdropper can't even see who sent what.

KDF_RK_HE + AES-CBC + HMAC
// Header key derived from each root key function KDF_RK_HE(rk): return HKDF(rk, "HeaderKey", 64) // 32B enc + 32B auth // Per-message header encryption (Section 4.2) header_key = KDF_RK_HE(rk_at_step) header_ct = AES-256-CBC(header_key.enc, iv=0, pad(dh_pub || PN || N)) header_mac = HMAC-SHA256(header_key.auth, header_ct)
Why bother? Without header encryption, a passive observer sees "user A sent 50 messages, then user B replied with a new DH key" — leaking traffic patterns. Encrypting the header with a different root-key-derived key per step makes even the metadata opaque.
05

SPQR — Sparse Post-Quantum Ratchet (Section 5)

The DH ratchet is secure against classical computers, but a future quantum computer could break Diffie-Hellman. SPQR adds a second, slower ratchet that uses a post-quantum key encapsulation (ML-KEM, formerly Kyber). It runs less often — every few messages — because post-quantum ops are heavier.

SCKA — Symmetric Cryptographic Key Agreement
  • KDF_SCKA_INIT — initialise from a PQC shared secret
  • KDF_SCKA_RK — root-chain step (analogous to KDF_RK but post-quantum)
  • KDF_SCKA_CK — chain step (analogous to KDF_CK)
ML-KEM Braid

SPQR's primitive is an ML-KEM Braid: a small batch of ML-KEM encapsulations whose shared secrets are combined into the SCKA chain. This gives redundancy: even if a single KEM output is later broken, the others still hold the chain together.

The "harvest now, decrypt later" threat. Adversaries are recording encrypted traffic today so they can decrypt it once quantum computers exist. SPQR makes that strategy ineffective for the messages it covers — even a future quantum adversary can't retroactively break ML-KEM.
06

Triple Ratchet — Double Ratchet + SPQR in parallel (Section 6)

The Triple Ratchet runs the classical Double Ratchet and SPQR side by side. Each step produces two root keys; a final KDF_HYBRID combines them. The result has the speed of classical crypto, the quantum-resistance of post-quantum crypto, and the failure modes of whichever side breaks first.

KDF_HYBRID — combining two ratchets
// Final step of each ratchet — combine classical and PQ outputs function KDF_HYBRID(rk_classical, rk_pq): return HKDF( ikm = rk_classical || rk_pq, salt = "TripleRatchetHybrid", info = "", L = 64 ) // new RK || CK
Why hybrid?
A single primitive can fail. Combining X25519 (classical) with ML-KEM (PQ) means the session is safe unless both are broken at once — which is extremely unlikely.
Performance
SPQR steps happen less often (e.g. every 10 messages) because ML-KEM is bigger and slower. Classical X25519 stays in the per-message path.
Migration path
Old clients can still talk to new ones: the classical Double Ratchet continues to work alone, and SPQR adds on top when both sides support it.
07

PQXDH — how the first key gets there (Section 7.1)

The Double Ratchet needs a starting secret (SK, 32 bytes). That secret comes from PQXDH (Post-Quantum Extended Triple Diffie-Hellman) — a one-shot key agreement performed when Alice first messages Bob. PQXDH blends X25519 (classical) with ML-KEM (post-quantum), so the very first message benefits from the same hybrid protection as the rest of the session.

What PQXDH delivers
  • A 32-byte shared secret SK
  • The initial RK fed into the first DH ratchet step
  • One-shot: it runs once per session, not per message
  • If the recipient is offline, the sender's prekey bundle carries the PQ part
Where PQXDH stops and Double Ratchet starts. PQXDH answers "how do two strangers agree on a secret over an untrusted network?" The Double Ratchet answers "now that we share a secret, how do we keep it secret for the next 10,000 messages?"

09

Security properties at a glance

Forward secrecy

Compromising today's key doesn't reveal past messages. Provided by the symmetric ratchet: each MK is one-way derived from the previous chain key.

Post-compromise security

Compromising today's key doesn't reveal future messages — once the next DH ratchet step runs. The DH exchange mints a fresh key the attacker doesn't have.

Quantum resistance

Only with SPQR enabled (Section 5/6). Plain Double Ratchet's X25519 DH can be broken retroactively by a future quantum computer. The Triple Ratchet hybrid combines both.

Out-of-order delivery

The receiver caches skipped message keys in MKSKIPPED with a cap (MAX_SKIP) so an attacker can't make the receiver store millions of keys via spam.

One sentence to remember. The Double Ratchet gets a brand-new message key from a one-way function on every send (cheap, fast), and a brand-new root key from a fresh Diffie-Hellman on every direction change (heals the channel). SPQR adds a slower post-quantum ratchet on top, and the Triple Ratchet combines both so neither side alone is the weak link.
