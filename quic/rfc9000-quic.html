QUIC

A connection-oriented transport built on UDP that folds in the jobs TCP and TLS used to split between them. One handshake negotiates both crypto and transport. The connection is identified by a connection ID rather than an IP address, so it survives the network changing underneath it. And almost every header byte is encrypted, which is as much an anti-ossification measure as a privacy one — middleboxes cannot freeze a field they cannot read.

J. Iyengar (ed.) Fastly M. Thomson (ed.) Mozilla Version 0x00000001 ISSN 2070-1721
The whole spec in five lines
  • An application sees independent ordered byte streams. Loss on one stream does not stall the others — the head-of-line blocking that TCP forces on any multiplexed protocol above it.
  • A UDP datagram carries one or more packets; each packet's payload is a sequence of frames. Frames carry everything: stream data, acknowledgements, flow-control limits, connection IDs, close signals.
  • The handshake is TLS 1.3, carried in CRYPTO frames rather than TLS records, and it negotiates transport parameters in the same round trip as the keys.
  • Every packet is authenticated in full and encrypted as far as is practical. Only a handful of fields are readable on the wire, and RFC 8999 pins exactly which ones stay stable across versions.
  • Connection IDs decouple the connection from the 4-tuple. A client can change address mid-connection, or be NAT-rebound, and keep the connection after a challenge-response proves the new path works.

01 What QUIC actually is

QUIC is not "TCP over UDP". It is a transport that takes four problems the TCP+TLS stack cannot fix without breaking deployed middleboxes, and fixes them by moving the whole transport into userspace behind an encrypted envelope. UDP is the delivery mechanism, chosen "to better facilitate deployment in existing systems and networks" (§1) — nothing more.

Problem 1

Head-of-line blocking

TCP delivers one ordered byte stream. HTTP/2 multiplexes many logical streams inside it, so a single lost segment stalls delivery of every stream behind it. QUIC's streams are separately ordered: loss on stream 4 does not hold up stream 8.

Problem 2

Stacked handshakes

TCP's SYN exchange then TLS's own handshake are sequential, because TLS cannot start until the connection exists. QUIC merges them — one exchange settles keys, transport parameters, and the application protocol (ALPN, which §7 makes mandatory).

Problem 3

Ossification

TCP headers are in cleartext, so middleboxes came to depend on them, and the header can no longer change. QUIC "authenticates the entirety of each packet and encrypts as much of each packet as is practical" — a field nobody can read is a field nobody can freeze.

Problem 4

Address pinning

A TCP connection is its 4-tuple; change the IP and it is gone. QUIC packets carry a connection ID chosen by the receiver, so a Wi-Fi-to-cellular switch or a NAT rebinding becomes a path change rather than a connection failure.

One protocol, three documents

RFC 9000 defines streams, connections, packets, frames, and the state machines. It deliberately leaves out two things, because they change at a different pace than the wire format does.

One asymmetry to keep in mind
Only clients migrate. §9 restricts connection migration to new client addresses, with one exception: a server can advertise a preferred_address and have the client move there after the handshake (§9.6). Servers never send non-probing packets to a client address until they have seen a non-probing packet from it — otherwise an attacker could redirect a server's traffic at a victim by spoofing.
02 The handshake

QUIC carries the TLS 1.3 handshake inside CRYPTO frames. TLS's own record layer is unused — QUIC does the framing, the reliability, and the encryption itself. What TLS supplies is the key exchange, the authentication, and a transport-parameters extension that rides along in the same messages.

§7 lists what the cryptographic handshake must deliver: an authenticated key exchange where the server is always authenticated and the client optionally is; keys that are distinct per connection; an authenticated exchange of both endpoints' transport parameters, with confidentiality for the server's; and an authenticated application-protocol negotiation.

Three packet number spaces

This is the structural idea that makes the handshake work. Packets are partitioned into three spaces, each with its own keys, its own packet numbers starting at 0, and its own acknowledgements. An Initial packet can only be acknowledged by an Initial packet.

Initial space

Initial packets

Protected with keys derived from the client's first Destination Connection ID — a value visible to anyone on the path. This is obfuscation, not confidentiality: it lets a receiver detect tampering and keeps middleboxes from parsing, but it is not a secret.

Handshake space

Handshake packets

Protected with real TLS handshake keys. §8.1 notes the consequence: successfully processing a Handshake packet implicitly validates the peer's address, because producing one requires having received the peer's Initial.

Application space

0-RTT and 1-RTT packets

These share a number space, deliberately: it "makes loss recovery algorithms easier to implement between the two packet types". A server acknowledges 0-RTT data in 1-RTT packets, and the client's 1-RTT packets simply continue the same numbering.

CRYPTO offsets restart per space
Each space has its own CRYPTO frame offset sequence starting at zero. So "offset 0" in the Initial space and "offset 0" in the Handshake space are different bytes of the TLS handshake. Unlike stream data, CRYPTO frames are not flow controlled — the corresponding backstop is CRYPTO_BUFFER_EXCEEDED (§20.1), which closes the connection when a peer sends more handshake data than the receiver can hold.

0-RTT and the price of it

A client that has connected before can send application data in its very first flight, in 0-RTT packets. Two constraints follow from that, both in §7.4.1.

Remembered parameters

The client must use the transport parameters it remembered from the previous connection, since the new ones have not arrived yet. A server that accepts 0-RTT must not reduce most limits below what it previously advertised — doing so is a PROTOCOL_VIOLATION.

No replay protection

0-RTT data can be captured and replayed by an attacker; QUIC cannot prevent it. §21 pushes the problem up the stack: only the application protocol knows which of its operations are safe to repeat.

Note also what HANDSHAKE_DONE is for. It is sent by the server only, in a 1-RTT packet, and it tells the client the handshake is confirmed. Until that point the client must not migrate (§9), and neither side can discard the Handshake keys.

03 Packets and frames

Three levels of nesting, and it is worth being precise about them because the spec's language depends on the distinction. A UDP datagram carries one or more QUIC packets. Each packet has a header and an encrypted payload. That payload, once decrypted, is a sequence of frames. Frames never span packets.

§12.2 — coalescing. Packets from different number spaces travel in one datagram, cutting the handshake to about four round-trip-worth of datagrams.

Why the short header has no Length field
Long headers carry an explicit Length, which is what makes coalescing work: a receiver can find where one packet ends and the next begins. The short header has no such field — a 1-RTT packet runs to the end of the datagram. So a 1-RTT packet can only ever be the last packet in a datagram.

Byte 0

Everything that distinguishes one packet type from another lives in the first byte. Only the top two bits are readable by an observer; the rest is covered by header protection (RFC 9001 §5.4) and is unreadable without keys.

The spin bit is deliberate leakage
One bit, in the clear, that flips once per round trip so a passive observer can measure RTT (§17.4). It is optional, and endpoints that implement it should disable it on a random fraction of connections — otherwise "always off" itself becomes a fingerprint. It exists because operators needed something measurable after TCP's timestamps disappeared behind encryption.

Packet numbers

  • A 62-bit integer, but encoded in the header on 1 to 4 bytes: the sender transmits only enough low bits for the receiver to reconstruct the full value unambiguously, given what it has already acknowledged.
  • Never reused within a space. The packet number feeds the AEAD nonce, so reuse would be a nonce reuse. Retransmitting lost data means putting the same frames into a new packet with a new number.
  • Must increase by at least one per packet, but gaps are legal — and useful, since they make it harder to correlate a sender's packets across paths.
  • If a sender ever reaches 262−1, it MUST close the connection without sending CONNECTION_CLOSE, since sending it would need one more number.
This is the retransmission model
QUIC never retransmits a packet. It retransmits the frames that were in a lost packet, repackaged into a new packet. That is why §12.4 can say "all frames are idempotent" — receiving one twice must be harmless, because the sender has no way to guarantee it did not already arrive.

Two rules with teeth
A frame in a packet type it is not permitted in is a connection error of type PROTOCOL_VIOLATION. An unknown frame type is FRAME_ENCODING_ERROR. And though frame types are variable-length integers, they are the one place where the shortest encoding is mandatory — 0x4001 is a legal two-byte encoding of the value 1, but a PING frame is always the single byte 0x01.
05 Streams

A stream is an ordered byte sequence and nothing more — QUIC preserves no message boundaries, and STREAM frame boundaries are explicitly not expected to survive retransmission. Streams are cheap: there is no open handshake, and §2 notes that "a single STREAM frame can open, carry data for, and close a stream".

Reading a stream ID

A stream ID is a 62-bit integer, and its two low bits are not part of the number — they are the type. This is what removes the need for any negotiation about who may use which IDs.

§2.1 — the two low bits
// bit 0x01 — who opened it
0 → client-initiated   // even stream IDs
1 → server-initiated   // odd stream IDs

// bit 0x02 — which way it flows
0 → bidirectional
1 → unidirectional

// so, four independent ID spaces, each starting at its own low value:
0x00  client-initiated, bidirectional    // 0, 4, 8, 12, ...
0x01  server-initiated, bidirectional    // 1, 5, 9, 13, ...
0x02  client-initiated, unidirectional   // 2, 6, 10, 14, ...
0x03  server-initiated, unidirectional   // 3, 7, 11, 15, ...
Opening one stream can open several
Streams of a type must be created in increasing order — but you may skip ahead. Using stream 12 when you have only used 0 and 4 implicitly opens 8 as well. That is what makes a lost or reordered STREAM frame harmless: the receiver's view of which streams exist does not depend on arrival order.

The two half-lives of a stream

§3 models each direction separately: a sending part and a receiving part. A bidirectional stream is just both, superimposed. Every terminal state below is reached in one of exactly two ways — the data ended cleanly, or it was reset.

Sending side — §3.1
  • Ready — the stream exists but nothing has been sent.
  • Send — sending STREAM frames, subject to flow control.
  • Data Sent — the FIN has gone out; the final size is now fixed and only retransmissions remain.
  • Data Recvd — everything, including the FIN, has been acknowledged. Terminal.
  • Reset Sent → Reset Recvd — the alternative ending, via RESET_STREAM.
Receiving side — §3.2
  • Recv — accepting data, buffering out-of-order arrivals up to the advertised limit.
  • Size Known — the FIN arrived, so the final size is known even if holes remain.
  • Data Recvd — the byte stream is complete. Terminal once read by the application.
  • Reset Recvd — a RESET_STREAM arrived; the application is told the stream aborted.

Cancelling a stream: two frames, one direction each

RESET_STREAM — I am done sending

Abruptly ends the sender's half. It carries the final size, and that number is why cancelling a stream cannot be used to escape flow control: those bytes still count against the connection limit whether they were delivered or not.

STOP_SENDING — please stop

A receiver's request that the peer stop. It has no direct effect; the peer is expected to answer with RESET_STREAM. Without it, a receiver that has abandoned a stream would have to keep granting it flow-control credit to avoid stalling the connection.

Prioritisation is not here
§2.3 acknowledges that stream scheduling has a large effect on performance, and then declines to specify anything: "QUIC does not provide a mechanism for exchanging prioritization information." The application protocol owns it — for HTTP/3, that is RFC 9218. What QUIC does give an implementation is the API surface to act on it.
06 Flow control

A receiver has to buffer out-of-order data to deliver an ordered stream, and it cannot let a peer decide how much memory that costs. QUIC's answer is credit, granted along three separate axes — and the per-connection axis is the one that stops a peer opening a thousand streams to multiply its allowance.

Axis 1 — per stream

MAX_STREAM_DATA

The largest byte offset the peer may reach on this stream. Initial values arrive as transport parameters, one per stream type: initial_max_stream_data_bidi_local, …_bidi_remote, …_uni.

Axis 2 — per connection

MAX_DATA

The total across all streams. Bounds the receiver's memory regardless of how the peer distributes its traffic. Starts at initial_max_data.

Axis 3 — stream count

MAX_STREAMS

How many streams of each type the peer may open. Bounds per-stream bookkeeping, not bytes. Starts at initial_max_streams_bidi / _uni — and if either is absent or zero, the peer cannot open that kind of stream at all until a MAX_STREAMS arrives.

Absolute values, never deltas
Every limit frame carries the new ceiling, not an increment, and limits only ever increase — a frame that would lower one is simply ignored. This makes the whole mechanism immune to reordering and duplication, which matters because QUIC gives no ordering guarantee between frames in different packets. A receiver that lowered a limit would be a FLOW_CONTROL_ERROR waiting to happen; the spec removes the possibility.

The blocked frames are telemetry, not requests

DATA_BLOCKED, STREAM_DATA_BLOCKED, and STREAMS_BLOCKED announce that a sender has been stopped by a limit. They ask for nothing. Their value is diagnostic: §4.1 points out that a receiver seeing them knows its own limits — or its own tuning — are what is capping throughput, rather than the network.

07 Connection IDs and migration

Each endpoint chooses the connection IDs its peer writes into packets sent to it. That inversion is the whole trick: a connection ID only has to be meaningful to its issuer, so a server can encode routing information in it and a load balancer can steer on it without terminating the connection.

The mechanics
  • Up to 20 bytes in version 1. A longer value in a v1 long header means drop the packet.
  • Zero-length is legal — for a client that never needs packets routed to it by ID. The cost is that it cannot then multiplex connections on one IP and port if migration, NAT rebinding, or port reuse are in play.
  • Each gets a sequence number. NEW_CONNECTION_ID issues one; RETIRE_CONNECTION_ID gives it back. A "Retire Prior To" field lets the issuer force a bulk rotation.
  • active_connection_id_limit caps how many the peer may hold. Minimum 2, default 2; advertising less than 2 is a TRANSPORT_PARAMETER_ERROR. Two is the floor because migrating requires having a spare.
  • The same connection ID must never be issued twice, and IDs must carry nothing that lets an outside observer link them. Otherwise the whole privacy story collapses.

Path validation

When a packet arrives from an address that has not been validated, the endpoint must probe that path before it commits to it. §9.1 splits frames into probing (PATH_CHALLENGE, PATH_RESPONSE, NEW_CONNECTION_ID, PADDING) and everything else, non-probing. A packet made only of probing frames tests a path without moving the connection to it.

§8.2 and §9 — path validation, then migration. Both are just frames; there is no separate handshake.

Not every address change is a migration

A NAT reallocating a port produces the same observable event as a deliberate migration, and the endpoint cannot tell them apart. Either way it must run path validation. §9.3.3 also covers the nastier case: an attacker who forwards packets from a spoofed address can trigger a migration, and the fix is that the original path stays validated, so the endpoint can fall back to it.

Migration is a privacy event

§9.5 is blunt: an endpoint that migrates must use a fresh connection ID, and should not reuse one across paths. Otherwise an observer who sees the same connection ID on two networks has linked the user's home IP to their office IP — exactly the correlation connection IDs were introduced to prevent.

Two transport parameters that constrain all this
disable_active_migration — a zero-length flag saying "do not move off the address you handshook on". A server behind a stateful load balancer typically sets it.
preferred_address — the server's invitation to move to a different address after the handshake, bundled with a connection ID at sequence number 1 and its reset token, so the client always has an unused ID ready for the move.
08 Address validation and datagram size

UDP has no handshake, so anyone can send a QUIC server a packet with a forged source address and have the reply land on a victim. If the reply is bigger than the request, the server has become an amplifier. §8 and §14 are the two halves of the defence, and they are tightly coupled.

The rule

Three times, no more

"After receiving packets from an address that is not yet validated, an endpoint MUST limit the amount of data it sends to the unvalidated address to three times the amount of data received from that address."

Bytes are counted across all datagrams attributable to the connection — including ones whose packets were discarded entirely. An attacker gets no credit for sending garbage, but the victim gets no extra exposure either.

The complement

Pad the Initial to 1200

A client MUST expand every datagram carrying an Initial packet to at least 1200 bytes, with PADDING frames or by coalescing. Two effects at once: it proves the path can carry a usable MTU in both directions, and it raises the numerator of the 3× budget so the server can actually fit its certificate chain into the first flight.

A server MUST discard an Initial arriving in a smaller datagram, and MAY close with PROTOCOL_VIOLATION.

The deadlock the 3× limit creates
A server hits its anti-amplification limit and stops. The client has acknowledged everything it sent and has no reason to speak. Nobody moves, and the handshake hangs. §8.1's fix is a client obligation: send a packet on every Probe Timeout — a padded 1200-byte Initial if it lacks Handshake keys, otherwise a Handshake packet. Each one buys the server another 3× of budget.
09 Termination, errors, and stateless reset

Three ways a connection ends, and they differ in what state the endpoint has left. That is the axis worth holding onto: CONNECTION_CLOSE needs keys and connection state, idle timeout needs neither party to act, and stateless reset exists precisely for the case where all state is gone.

Idle timeout — §10.1

Both sides just stop

Each endpoint may advertise max_idle_timeout; the effective value is the minimum of the two non-zero values. If both omit it or send 0, there is no idle timeout at all. To avoid a race where both sides silently disagree, an endpoint must not close on idle before three PTOs have elapsed.

Immediate close — §10.2

CONNECTION_CLOSE

Sender enters the closing state: it sends nothing new, but re-emits the close frame in response to incoming packets, rate-limited. Receiver enters the draining state: it sends nothing at all. Both last about three PTOs, long enough to absorb in-flight packets so the peer is not left retransmitting into a void.

Stateless reset — §10.3

Last resort

An endpoint that has lost its connection state — a crash, a restart, a load balancer moving the flow — cannot produce a valid CONNECTION_CLOSE, because that needs keys. It sends a stateless reset instead, and the peer tears the connection down immediately.

The shape of a stateless reset

The design constraint is unusual and worth stating plainly: the reset must be indistinguishable from an ordinary 1-RTT packet to anyone but its recipient. If it were recognisable, an off-path attacker could forge one and kill connections at will.

Padding as camouflage
The minimum viable reset is 21 bytes, but that is not enough to hide it if the recipient uses long connection IDs — a short datagram could not have held one. So §10.3 asks endpoints to pad all their outgoing packets to at least 22 bytes more than the connection ID length they ask their peer to use. That way, any stateless reset the peer might send is the same size as ordinary traffic. A reset answering a datagram of 43 bytes or fewer must itself be one byte shorter than what it replies to — so resets can never loop.

Connection errors and stream errors

§11 draws the line: an error that leaves the connection unusable is a connection error and ends everything with CONNECTION_CLOSE. An error confined to one stream is a stream error and costs only that stream, via RESET_STREAM. Most protocol violations are the former.

10 Wire encoding

Two encodings account for most of the format: the variable-length integer that nearly every field uses, and the transport parameter list that the handshake carries.

Variable-length integers

The two most significant bits of the first byte hold the base-2 logarithm of the total length in bytes. The remaining bits are the value, big-endian. So a small number costs one byte, and the encoding still reaches 262−1.

Three fields that are not varints
Versions (§15) are a fixed 32 bits. Packet numbers in a header (§17.1) are 1–4 raw bytes with the length in the first byte's low bits. Connection ID lengths in a long header (§17.2) are a plain 8-bit integer. All three are version-invariant fields — they have to be parseable by an endpoint that does not know the version, so they cannot use a version-specific encoding.

Transport parameters

Carried in a TLS extension and therefore authenticated by the handshake, with confidentiality for the server's set. Every parameter is a varint identifier, a varint length, and a value. Absent means zero, unless the parameter says otherwise — which for several of them means "the peer may not do this at all".

Why 0x00, 0x0f, and 0x10 exist
All three are connection IDs echoed back, and together they close the same hole. Connection IDs are chosen before any keys exist, so an on-path attacker can rewrite them in Initial packets without detection. By having each side restate, inside the authenticated handshake, which connection IDs it originally used, both endpoints can verify afterwards that nothing was tampered with. §7.3 requires the check, and a mismatch is a TRANSPORT_PARAMETER_ERROR.
