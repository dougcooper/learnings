Certificate-Bound OAuth Tokens

In bearer-token OAuth, whoever holds the access token holds the access. RFC 8705 — OAuth 2.0 Mutual-TLS Client Authentication and Certificate-Bound Access Tokens — upgrades the client credential from a shared secret to a TLS client certificate, and pins issued access tokens to that certificate via a cnf.x5t#S256 thumbprint. A stolen token is then unusable without the private key it was bound to.

B. Campbell Ping Identity J. Bradley Yubico N. Sakimura NRI T. Lodderstedt YES.com AG ISSN 2070-1721
The whole spec in four lines
  • Two registered authentication methods let a client authenticate to the token endpoint with a TLS client certificate: tls_client_auth — a PKI-validated chain matched by one subject DN or SAN — or self_signed_tls_client_auth — a certificate registered up front in the client's jwks.
  • Independently of authentication, the authorization server can bind the issued token: a JWT carries cnf: { "x5t#S256": ... }, the base64url SHA-256 of the certificate's DER encoding; introspection returns the same structure for opaque tokens.
  • At the protected resource, mTLS becomes pure proof-of-possession: the RS pulls the client certificate out of its TLS stack, hashes it, and MUST reject with 401 invalid_token unless the thumbprint matches the token's.
  • The two mechanisms are complementary but orthogonal — token binding without client authentication is exactly what public clients do (§7).

01 The bearer-token problem

The abstract OAuth 2.0 flow of RFC 6749 has three moves: (A) the client authenticates to the authorization server and gets an access token; (B) it presents the token to a protected resource; (C) the resource validates it — locally for self-contained tokens, or remotely via introspection. TLS protects steps A and B on the wire, but once issued, a bearer token is a bare capability: RFC 6750 gives the resource no way to tell the legitimate client from whoever copied the string.

What the bearer model gives up

Possession is the only credential

Any party in possession of the token can use it — for its whole lifetime, wherever it leaks. Replay, token theft, misdirected logs, and compromised proxies all end the same way. The token binds to no holder at all.

The upgrade path

Proof-of-possession

Bind the token to an asymmetric key and require the presenter to prove possession of the private key — what the spec calls key confirmation, holder-of-key, or proof-of-possession. A stolen token then has no value without the key. mTLS supplies exactly this proof: the TLS handshake makes the client sign (CertificateVerify) with the certificate's private key.

Where OAuth already authenticates

Not just the token endpoint

RFC 6749 defines client_secret_basic / post — shared secrets. Its extensions also authenticate clients: introspection (RFC 7662), revocation (RFC 7009), CIBA's backchannel. RFC 8705 defines one better credential usable at every endpoint that authenticates a client.

A better credential, and a new validation duty
The document therefore standardizes two things at once: step (A) — mutual-TLS as a client authentication method, with better security characteristics than shared secrets — and step (C) — semantics that let a protected resource, local or remote, verify the presenter matches the certificate the token was issued against. The methods also apply to every OAuth endpoint that uses client authentication, not only the token endpoint.
02 Two mechanisms, independent

The single most misread sentence of the RFC is this: mutual-TLS client authentication and certificate-bound access tokens are distinct mechanisms that are complementary but don't need to be deployed or used together. One is about who is calling the token endpoint; the other is about who may present the token.

The public-client surprise
A client can bind tokens without any client authentication at all (§7): individual instances of a public client mint self-signed certificates, and the AS binds their tokens to whichever certificate the TLS handshake proved possession of — without using it as an OAuth credential. See §7.
03 Client authentication, two ways

An extension of RFC 6749 §2.3. The TLS connection to the authorization server MUST have been established — or re-established — with mutual-TLS X.509 certificate authentication: in contemporary TLS (1.3 included) that means the client sent Certificate and CertificateVerify during the handshake, and the server verified them plus Finished. Every such request MUST also include client_id, so the server can look up the expected credential independently of the certificate's contents. No certificate, or a certificate that doesn't match what is registered for that client_id, and the server answers with a normal OAuth error: invalid_client (RFC 6749 §5.2).

Example registration — constructed from §2.1.2 + §3.4 metadata
{
  "client_id": "s6BhdRkqt3",
  "token_endpoint_auth_method": "tls_client_auth",
  "tls_client_auth_subject_dn": "CN=api-client.example.com, O=Example Corp, C=US",
  "tls_client_certificate_bound_access_tokens": true
}

The PKI method identifies the client by exactly one subject value registered with the AS. A client using tls_client_auth MUST register exactly one of:

PKI method (§2.1) — the chain is validated per RFC 5280, then one subject value is matched. Revocation checking is a deployment decision.

PKI method — tls_client_auth

Trust the CA, match the subject

The traditional use of X.509: TLS validates possession of the private key and the certificate chain; the AS additionally checks that the certificate's single registered subject (DN or one SAN value) matches what the client registered.

Rotation is free: get a new certificate with the same subject from a trusted CA and nothing at the AS changes.

Self-signed method — self_signed_tls_client_auth

Trust the registration, skip the CA

The client registers its certificates up front in jwks / jwks_uri — each as the x5c of a JWK. TLS still proves private-key possession, but the chain is not validated; the certificate presented must match one of the registered ones.

RFC 7517 §4.7 requires the first x5c certificate to match the JWK's key members (n/e, x/y) — which stay mandatory even though unused here. Rotation via a jwks_uri the AS re-reads.

The PKI method's open flank — §7.4
Matching on subject means any certificate the AS trusts with the same DN or SAN authenticates the client. An attacker holding a same-subject certificate from a different CA that the AS trusts wins. The mitigation is blunt: the AS SHOULD accept a limited set of CAs whose issuance policy it knows, with the trust-anchor set agreed out of band. Without that assumption, subject identification is a spoofing liability.
04 Binding at issuance: cnf and x5t#S256

When the token request arrived over the mutual-TLS connection, the AS knows which certificate the client holds. For the token to be usable elsewhere, the binding travels with the token: the certificate's hash is embedded at issuance, either inside the JWT itself (§3.1) or in the introspection response for opaque tokens (§3.2). For JWTs the hash SHOULD use the x5t#S256 confirmation method defined here, inside the cnf (confirmation) claim that RFC 7800 already specified.

Figure 2 — JWT claims set with the certificate thumbprint
{
  "iss": "https://server.example.com",
  "sub": "ty.webb@example.com",
  "exp": 1493726400,
  "nbf": 1493722800,
  "cnf":{
    "x5t#S256": "bwcK0esc3ACC3DB2Y5_lESsXE8o9ltc05O89jdN-dg2"
  }
}

The value is base64url(SHA-256(DER-encoding of the certificate)). The RFC is specific about the encoding: base64url without trailing '=' padding, and no line breaks, whitespace, or embellishment of any kind. Why DER? Because DER is canonical — one certificate, one byte sequence, so independent implementations hash identical input. (The same canonicity argument forces DER on the raw public keys of RFC 7250, where the certificate itself is dropped and a bare SubjectPublicKeyInfo travels in the Certificate message instead.)

RFC 7662 responses gain a top-level cnf member with the same semantics and format as the JWT claim — registered in §9.4.

Note what issuance did not do: bind the token to the TLS connection. The binding is to the certificate, agreed between token and metadata — which is what decouples client authentication from protected-resource access, and what lets mTLS at the resource server serve purely as proof-of-possession.

Other bindings are allowed
The cnf.x5t#S256 structure is what the spec defines, but it expressly notes that other methods of associating a certificate with a token are possible by AS↔RS agreement — they're just out of scope. If your AS and RS already speak a holder-of-key dialect, RFC 8705 doesn't forbid it; it standardizes the interoperable one.
05 Proof at the resource server

The resource server's duties are short and categorical. On the connection it obtains the client certificate from its TLS implementation layer; it computes the SHA-256 over the DER bytes; it compares against the token's cnf.x5t#S256 — decoded straight out of a JWT, or fetched by introspecting the token. Match: the request proceeds. No match — because the certificate is wrong, absent, or a different one reused: MUST reject with HTTP 401 and the invalid_token error code of RFC 6750.

Read the requirements in order — each is load-bearing:

The resource-server checklist — §3
  • Access requests MUST ride a mutually authenticated TLS connection using the same certificate used at the token endpoint.
  • The RS MUST obtain the client certificate from its TLS layer and MUST verify it matches the certificate bound to the token.
  • Mismatch ⇒ reject with 401 + invalid_token per RFC 6750.
  • The RS must expect mTLS in advance — it cannot learn it from the token, which is application data arriving only after the handshake. The RFC makes no provision for TLS 1.2 renegotiation or TLS 1.3 post-handshake authentication to retro-fit a client cert.
How RS policy and AS policy stay in sync
They don't — the question is out of scope for the document. In practice the RFC observes two shapes: an RS requires mTLS for everything it hosts, or it serves mTLS-protected and ordinary resources on separate hostname:port combinations. The AS-side equivalent is mtls_endpoint_aliases.
The RS never validates the chain — §6.2
OAuth's division of labor puts client authentication at the AS; the RS "does not directly authenticate the client per se". So for both methods the RS configures TLS to not verify that the client certificate is signed by a trusted CA. The thumbprint comparison is the whole game: the identity work happened at issuance, mTLS here is only proof-of-possession. (Compare RFC 7250, where the same "trust comes from out-of-band knowledge" reasoning eliminates the certificate entirely.)
06 Discovery, capability flags, and aliases

Three pieces of metadata advertise the machinery. The AS publishes tls_client_certificate_bound_access_tokens (§3.3, default false) to signal it can issue bound tokens; the client registers the same-named parameter (§3.4) to declare its intention. A client that declared the intention but hits the token endpoint without mTLS is an AS-policy question — the server MAY error or issue an unbound token.

The third piece exists because of a TLS quirk: a server cannot silently receive a client certificate — it has to request one, and some clients behave badly when asked. Web browsers in particular pop an intrusive certificate-selection prompt. An AS serving conventional and mTLS clients in parallel MAY park its certificate-requesting behavior on dedicated endpoints:

{
  "issuer": "https://server.example.com",

  "revocation_endpoint": "https://server.example.com/revo",
  "token_endpoint_auth_methods_supported":
      ["tls_client_auth","client_secret_basic","none"],
  "tls_client_certificate_bound_access_tokens": true,
  "mtls_endpoint_aliases": {
    "token_endpoint": "https://mtls.example.com/token",
    "revocation_endpoint": "https://mtls.example.com/revo",
    "introspection_endpoint": "https://mtls.example.com/introspect"
  }
}

A client intending mTLS MUST prefer the alias URL when present. Aliases may point at a different host (as here) so TLS behavior — with or without a server_name-based split, RFC 6066 — differs per host. Parameters in the alias object that aren't endpoints SHOULD be ignored.

Same certificate, two jobs, one TLS config question
Implementation notes (§6.1) follow directly: an AS supporting mTLS auth alongside other methods or public clients makes client certificates optional in the handshake; an AS doing only the self-signed method configures TLS to not chain-validate the client cert; and hosting mTLS endpoints on a distinct hostname or port is the structural fix for the browser-prompt problem.
07 Public clients, and where refresh tokens stand

A public client has no client credentials at all — so there is nothing to authenticate, yet per-instance token binding still works (§4). The TLS stack is configured exactly like the self-signed method: the AS doesn't check whether the presented certificate is CA-signed. Each instance mints its own self-signed certificate, uses it for mutual TLS with both the AS and the RS, and the AS — without treating the certificate as an OAuth credential — binds the issued token to the certificate whose private key the handshake just proved. Now the token belongs to the instance, not the client_id.

Client typeHow refresh tokens end up certificate-bound — §7.1
Confidentialauthenticated with tls_client_auth or the self-signed method RFC 6749 already requires binding the refresh token to the client and authenticating the client when it is presented — with certificate-based client auth, that makes the refresh token indirectly bound. No extra machinery.
Publicno credentials behind the client_id (§4) The AS SHOULD bind the refresh token to the same certificate the access token is bound to, and check that binding when the token is spent. How is left to AS implementers.
Why this matters more than it looks
Mobile and native apps are the classic public clients — single end-user, per-device instances. §8 flags the privacy angle that comes with them: in TLS versions before 1.3, the client certificate rides the handshake in cleartext, observable to anyone on path. A client acting for one user is thereby trackable; such clients should prefer TLS 1.3 (where the certificate is encrypted) or weigh what the older TLS exposes.
08 Sharp edges

The operational gotchas cluster in §6–§8; none of them are optional reading for an implementer.

Certificate rotation — §6.3

Rotating the cert invalidates live tokens

A bound token is useless the moment the client rotates to a new certificate — by design. The RFC says to handle it like token expiry: the client refreshes (a refresh token is not cert-bound the same way) and retries. Plan retries into the client.

Implicit grant — §6.4

Explicitly unsupported

Token binding is defined for tokens issued at the token endpoint. The implicit grant issues tokens from the authorization endpoint through the user's browser — where client certificates bring exactly the UX problems that motivated the aliases of §5. Use grant types where the client talks to the token endpoint itself: authorization code, refresh token.

TLS termination — §6.5

Load balancers are your problem

Terminating TLS at a proxy or LB is fine but the spec deliberately does not say how client-certificate metadata crosses that boundary securely. Whoever terminates TLS owns that plumbing — headers need protection, or the proof-of-possession guarantee evaporates.

Subject spoofing — §7.4

The CA set is the identity policy

Under the PKI method the only thing tying a certificate to a client is its subject. Any trusted CA that will issue a cert with that subject mints an impersonator. Restrict trust anchors; treat the CA set as part of the client registry.

X.509 complexity — §7.5

Do not write your own validator

Basic constraints, key-usage and critical extensions, validity windows, embedded NUL bytes in ASN.1 length-counted names, non-canonical name encodings, wildcards, recursive chain walking, revocation — the document cites the graveyard and SHOULD-s implementers into using an established X.509 library.

Why a hash at all — §7.2
Binding by thumbprint leans on SHA-256's second-preimage resistance: forging a different certificate with the same hash must be computationally infeasible. If certificate digests ever move to other hash functions, the intended mechanism is new members next to x5t#S256 in the IANA "JWT Confirmation Methods" registry — not silent re-use. And TLS practice comes from BCP 195, with the usual caution: a security document is a point-in-time statement — check errata.

Appendix B — versus Token Binding
OAuth 2.0 Token Binding, the RFC's conceptual sibling, pursues the same proof-of-possession goal with bare client-generated keys — no certificates, no PKI, none of §7.5's parsing hazards. Its problem, at time of writing, was platform support; mTLS, meanwhile, "has been around for some time and enjoys widespread support". The two are expected to coexist, possibly in the same AS serving different clients. The RFC chose the deployable-today route.

Related on this site: RFC 7250 — raw public keys in TLS trades the other half of this trade-off — certificate-bound tokens pin a certificate; raw public keys remove the certificate but leave nothing for a cnf.x5t#S256 thumbprint to pin.
