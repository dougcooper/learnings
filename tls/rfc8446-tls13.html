Not TLS 1.2 with better ciphers — a redesign that deletes every mode that could be misused, and folds key exchange into the first message so the handshake finishes in one round trip.

01 What changed §1.2, §2

The pivotal change is that the client guesses. Rather than waiting for the server to announce which key-exchange group it supports, the client sends a Diffie–Hellman public key in its very first message. If the guess is right — and it nearly always is — both sides compute a shared secret immediately, and every message after the server's first reply is encrypted.

TLS 1.2 — two round trips

RTT 1: ClientHello → ServerHello + Certificate + ServerKeyExchange → ClientKeyExchange + ChangeCipherSpec + Finished.

RTT 2: server Finished, then data.

  • Certificate travels in cleartext
  • Static RSA mode → no forward secrecy
  • MAC-then-encrypt CBC → padding oracles
  • Compression → CRIME
TLS 1.3 — one round trip

RTT 1: ClientHello with a key share → ServerHello with the matching share, then everything else encrypted.

The client's reply carries its Finished and can be followed immediately by application data.

  • Certificate encrypted
  • Ephemeral (EC)DHE only → always forward-secret
  • AEAD only → one-pass authenticated encryption
  • Compression removed entirely
Forward secrecy, briefly

Each connection generates a throwaway Diffie–Hellman key pair and discards it afterwards. An attacker who records the encrypted traffic and later steals the server's long-term private key still cannot decrypt it — that key only signs, it never encrypts the session. TLS 1.2's static-RSA mode lacked this property; TLS 1.3 deleted the mode rather than hardening it.

When the guess is wrong: HelloRetryRequest

If the client offered no key_share for a group the server accepts, the server replies with HelloRetryRequest and the client re-sends its ClientHello with the requested group. That costs the extra round trip TLS 1.3 normally avoids — which is why clients ship key shares for the groups servers actually use (X25519, P-256). Structurally, HelloRetryRequest is a ServerHello, distinguished only by a fixed sentinel value in its random field.

04 The key schedule §7.1

Every key TLS 1.3 ever uses comes out of one ladder. Two primitives do all the work. HKDF-Extract takes messy input — a Diffie–Hellman result, a pre-shared key — and condenses it into a uniform secret. HKDF-Expand-Label stretches that secret into as many distinct keys as needed; different labels yield provably unrelated keys from the same parent.

§7.1 — the key schedule, top to bottom

Rung 1 — Early Secret

Exists only so resumption and 0-RTT have something to derive from. On a fresh connection the input is a string of zero bytes and every output here goes unused.

Rung 2 — Handshake Secret

The first secret depending on fresh ephemeral material from both parties. This is the rung that delivers forward secrecy, and it is available the instant ServerHello lands.

Rung 3 — Master Secret

Derived once the transcript is complete, so every application key is bound to the exact messages both sides exchanged. Tampering anywhere upstream yields different keys and the connection fails.

From traffic secret to actual keys

A traffic secret is not itself an encryption key. Each direction expands its secret twice:

write_key = HKDF-Expand-Label(S, "key", "", key_len)
write_iv  = HKDF-Expand-Label(S, "iv", "", iv_len)

Ratcheting forward (KeyUpdate)

Long connections rotate keys without a new handshake:

secret_N+1 = HKDF-Expand-Label(secret_N, "traffic upd", "", Hash.len)

One-way — compromising secret_N+1 does not roll back to secret_N.

05 The record layer §5.1–5.5

Every TLS 1.3 cipher suite is AEAD — authenticated encryption with associated data. One primitive encrypts and authenticates in a single pass, eliminating the whole class of MAC-then-encrypt padding-oracle bugs that produced BEAST, Lucky13 and POODLE. The record format also hides more: the real content type moves inside the encrypted blob, and the outer header always claims to be application_data.

§5.2 — the true content type is encrypted; only the disguised header is visible

Per-record nonce  §5.3

No nonce is transmitted. Each side keeps a 64-bit sequence counter, left-pads it with zeros to the IV length, and XORs it with the static write_iv from the key schedule. Identical counters on both ends produce identical nonces without spending a byte on the wire.

The counter resets to zero on every key change and must never wrap — which is what KeyUpdate is for.

Key usage limits  §5.5

AEAD constructions degrade after enough records under one key. RFC 8446 gives concrete ceilings — for AES-GCM, roughly 224.5 records before a KeyUpdate is required. These are real cryptographic bounds, not formalities.

The five cipher suites

A TLS 1.3 cipher suite names only the AEAD and the hash. Key exchange and signature algorithm are negotiated separately by extension, so the combinatorial explosion of TLS 1.2 suite names disappears.

SuiteSupportNotes

06 Resumption & 0-RTT §2.2, §2.3, §4.6.1, §8

TLS 1.3 collapses session IDs and session tickets into a single mechanism: the pre-shared key. After a handshake completes, the server sends one or more NewSessionTicket messages, each a PSK identity the client can present later. Resuming with a PSK and a fresh key share gives a normal 1-RTT handshake with forward secrecy restored. Resuming with the PSK alone lets the client send data in its first flight — 0-RTT — at a real security cost.

§2.3 — 0-RTT: data rides with the first flight, before the server has said anything

0-RTT data is replayable. That is a design property, not a bug.

Early data is encrypted under a key derived only from the pre-shared key — nothing fresh from the server is mixed in yet. Two consequences follow. First, no forward secrecy: whoever later obtains the PSK can decrypt it. Second, an attacker who captures the early-data flight can replay it verbatim to the same server, or to a different server in the same cluster, and it will be accepted.

Rule of thumb: only send requests you would be comfortable having executed more than once. GET, not POST.

§8 — 0-RTT and Anti-Replay
Mitigation 1 — single-use tickets

The server records each ticket and rejects the second use. Effective, but requires shared state across a server fleet.

Mitigation 2 — ClientHello recording

Hash and store recent ClientHellos within a bounded time window, then reject duplicates. Bounded memory, bounded window.

Mitigation 3 — freshness checks

obfuscated_ticket_age lets the server verify the client's reported elapsed time is plausible, narrowing the replay window.

The PSK binder

The pre_shared_key extension must be the last extension in a ClientHello, because it carries an HMAC — the binder — computed over the ClientHello truncated immediately before the binder itself. This proves the client actually possesses the PSK rather than having copied a ticket identity observed on the wire.

07 What was deleted, and why §1.2

The most consequential part of RFC 8446 is a list of subtractions. Nearly every major TLS attack of the 2010s traced back to a legacy mode retained for compatibility; TLS 1.3 removed the modes instead of hardening them.

RemovedImpactWhy
Static RSA key exchangemajorEncrypting the premaster secret to the server's long-term key means no forward secrecy — and it powered ROBOT and Bleichenbacher-style oracles. All key exchange is now ephemeral (EC)DHE.
Static Diffie–Hellman suitesmajorSame forward-secrecy problem as static RSA.
CompressionmajorCompressing before encrypting leaks plaintext through ciphertext length. This was CRIME.
RenegotiationmajorA long history of injection attacks. Replaced by two narrowly-scoped post-handshake messages: KeyUpdate and post-handshake client auth.
Non-AEAD ciphers (CBC, RC4)majorMAC-then-encrypt CBC produced BEAST, Lucky13 and POODLE. RC4 was simply broken. AEAD only, now.
Custom / arbitrary DHE groupsmediumServers offering weak or malicious groups enabled Logjam. Only named, vetted groups remain.
RSA PKCS#1 v1.5 signaturesmediumReplaced by RSASSA-PSS, which has a proper security proof. v1.5 remains permitted inside certificates for ecosystem reasons.
DSA signatures; MD5 & SHA-1 in the handshakemediumObsolete, and in SHA-1's case collision-vulnerable — SLOTH.
ChangeCipherSpecminorNo longer meaningful — key changes are implied by message sequence. Survives only as an ignored dummy record for middlebox compatibility.
Session IDs & RFC 5077 ticketsminorTwo resumption mechanisms unified into one: PSK.
EC point format negotiationminorOne format (uncompressed) is mandated. One less thing to negotiate wrongly.

08 Downgrade defense §4.1.3, §4.2.1

An active attacker who strips the supported_versions extension could try to force both sides down to TLS 1.2 and attack that instead. TLS 1.3 defends with a sentinel hidden in plain sight: a TLS 1.3-capable server that ends up negotiating an older version must write a fixed byte string into the last 8 bytes of ServerHello.random.

§4.1.3 — downgrade sentinel values
negotiating TLS 1.2       :  44 4F 57 4E 47 52 44 01   // "DOWNGRD" + 0x01
negotiating TLS 1.1 or below:  44 4F 57 4E 47 52 44 00   // "DOWNGRD" + 0x00

A client that offered TLS 1.3 and sees this sentinel in a supposedly-1.2 response knows the downgrade was not the server's genuine choice, and aborts. Because ServerHello.random is covered by the TLS 1.2 Finished MAC, an attacker cannot strip the sentinel without breaking the handshake.

Version negotiation moved, and records lie about their version

The legacy_version field in ClientHello is frozen at 0x0303 (TLS 1.2) forever, because deployed middleboxes reject anything higher. Real negotiation happens in supported_versions. TLS 1.3 records also always claim to be TLS 1.2 on the wire — a deliberate disguise so middleboxes let them through. This, plus the dummy ChangeCipherSpec record and the echoed legacy_session_id, is what RFC 8446 calls middlebox compatibility mode.

§4.1.2, §4.2.1, Appendix D.4
Why the transcript hash keeps reappearing

Notice the recurring pattern: CertificateVerify signs the transcript, Finished MACs the transcript, and the Master Secret is derived from the transcript. Any modification an attacker makes to any handshake message, anywhere, produces a different hash — and the connection fails at the first check. That is the structural reason the handshake is tamper-evident as a whole rather than message by message.
