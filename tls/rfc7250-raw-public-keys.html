Raw Public Keys in TLS / DTLS

A certificate is a public key plus a signed set of claims about who owns it. If you already know who owns the key — because you provisioned it, or you looked it up in DNSSEC — the claims are dead weight. RFC 7250 lets the Certificate message carry just the key, and adds two extensions so both sides agree on which format is in the envelope.

P. Wouters (ed.) Red Hat H. Tschofenig (ed.) ARM J. Gilmore EFF S. Weiler Parsons T. Kivinen INSIDE Secure ISSN 2070-1721
The whole spec in four lines
  • The Certificate message becomes a container: it holds either an X.509 chain, as always, or a bare SubjectPublicKeyInfo.
  • Two extensions — client_certificate_type and server_certificate_type — negotiate which format goes in it, independently in each direction.
  • Nothing else changes. No new cipher suites, no new handshake messages, no change to key exchange or to how Finished is computed.
  • On its own it authenticates nothing. Binding that key to an identity happens entirely out-of-band — DANE, or a key burned in at manufacture.

01 The certificate you don't need

PKIX certificates solve a specific problem: you are talking to a stranger, and a third party you both trust vouches for their key. Plenty of TLS deployments are not that. The endpoints already know each other's keys, and the certificate is a formality that still has to be generated, shipped, parsed, and validated.

The status quo it replaces

Self-signed, distributed by hand

Small deployments already push self-signed certificates to every endpoint out-of-band. The trust comes from the distribution, not the signature — yet you still pay for certificate generation and parsing when none of the fields are used.

The driving use case

Smart objects over DTLS

A sensor speaking CoAP over DTLS can be configured at manufacture with its server's address and public key, plus its own key pair. Over-the-air bytes and firmware code size are both scarce; a chain validator is a lot of flash.

Keys arrive some other way

DANE, LDAP, firmware

A key can come from a DNSSEC-secured TLSA record, from a PKIX chain fetched over LDAP or the web, or from the OS image and its update channel. In all three, the in-band certificate is redundant with a path you already trust more.

The saving is not only transmission. A raw public key needs a minimalist ASN.1 parser and nothing else — no path building, no name constraints, no validity windows, no revocation checking. That code never ships, so it never has a bug.

"Raw" does not mean unencoded
The key is still a DER-encoded ASN.1 SubjectPublicKeyInfo — lifted verbatim out of the PKIX certificate format, length prefixes and algorithm OID included. RFC 7250 removes the certificate, not the encoding. If you want to go smaller still, it composes with the TLS Cached Info extension (RFC 7924), where peers exchange only fingerprints of keys they have already seen.
02 The container: one message, two shapes

No new message carries the key. The existing Certificate payload is redefined as a select over the negotiated certificate type — which is exactly why the negotiation in §3 is mandatory rather than optional. Without it, the receiver cannot tell an SPKI from a certificate list.

Figure 1 — Certificate payload as a container
opaque ASN.1Cert<1..2^24-1>;

struct {
    select(certificate_type){

         // certificate type defined in this document.
         case RawPublicKey:
           opaque ASN.1_subjectPublicKeyInfo<1..2^24-1>;

        // X.509 certificate defined in RFC 5246
        case X.509:
          ASN.1Cert certificate_list<0..2^24-1>;

        // "TLS Certificate Types" subregistry
    };
} Certificate;

What goes in the RawPublicKey arm is the standard PKIX structure from RFC 5280 §4.1. Note that it carries an algorithm identifier as well as the key material — so the receiver still learns "this is an RSA key" without any out-of-band agreement on algorithms.

One hard requirement
The value in the Certificate payload MUST be the DER encoding of the SubjectPublicKeyInfo — not BER, not a bare key. DER is canonical, so the structure is self-delimiting and every implementation produces identical bytes for the same key. That matters when an out-of-band mechanism has published a hash of those bytes.
03 Two extensions, two directions

This is the part people get backwards. There is no single "we're using raw public keys" flag. Each direction of authentication is negotiated on its own, so the client can present a raw key while the server presents an X.509 chain — or any other combination.

Figure 4 — CertTypeExtension structures
struct {
        select(ClientOrServerExtension) {
            case client:
              CertificateType client_certificate_types<1..2^8-1>;   // a list
            case server:
              CertificateType client_certificate_type;                // exactly one
        }
} ClientCertTypeExtension;

struct {
        select(ClientOrServerExtension) {
            case client:
              CertificateType server_certificate_types<1..2^8-1>;   // a list
            case server:
              CertificateType server_certificate_type;                // exactly one
        }
} ServerCertTypeExtension;

The same extension name means something different depending on who sent it. Read the grid one row at a time:

ExtensionIn ClientHelloIn ServerHello
client_certificate_typeabout the client's own credential "Here are the types I can provide if you send a certificate_request" — a list, in descending preference. "Send me this type" — one value, chosen from the client's list. Must be accompanied by a certificate_request.
server_certificate_typeabout the server's credential "Here are the types I can process when you send yours" — a list, in descending preference. "This is what is in my Certificate payload" — one value. This is what resolves the parsing ambiguity of §2.

Client side = a preference list. Server side = a single decision. Never more than one value in a ServerHello.

Values come from an existing registry
CertificateType is not new — it is the "TLS Certificate Types" subregistry, which already held X.509 (0) and OpenPGP (1). RFC 7250 adds RawPublicKey (2) and reuses the enum wholesale, which is why the extensions can negotiate formats this document never mentions. That registry-reuse design was contributed by Nikos Mavrogiannopoulos and is the reason the mechanism generalised beyond raw keys.
04 Negotiation rules

The whole protocol change lives in the two hello messages. Everything after that is ordinary TLS — Figure 5 below is just RFC 5246's handshake with two extensions bolted onto the hellos.

The normative rules are mostly about silence: don't advertise what you can't do, and don't say anything when X.509 is the answer.

WhoRule
Client MUST Omit from client_certificate_type any type it doesn't hold a credential for, or isn't configured to use with this server.
Client MUST Omit from server_certificate_type any type it cannot process.
Client MUST Omit the entire extension if the only type left is X.509 — that's the default, and saying so adds nothing.
Server MUST Include client_certificate_type in the ServerHello only together with a certificate_request, and pick a value from the client's list.
Server MUST Omit client_certificate_type when it isn't requesting a client certificate — or when nothing in the client's list is acceptable.
Server MUST Put the SubjectPublicKeyInfo in the Certificate payload if it answers RawPublicKey — and carry exactly one value in server_certificate_type.

On receiving a hello with either extension, a server lands in exactly one of three states:

Outcome 1

Doesn't know the extension

Replies with a normal ServerHello, extensions absent. Standard TLS extension behaviour — the client sees no answer and falls back to X.509 as the default, or gives up on its own terms.

Outcome 2

Knows it, no overlap

Terminates with a fatal unsupported_certificate alert. There is no negotiation round two, and no silent downgrade to a type neither side asked for.

Outcome 3

Knows it, has overlap

Selects one type per direction and echoes each as a single value. The rules in the table above apply from here on.

The client's preference is a preference, not a demand
In Figure 8 the client lists RawPublicKey first and still gets X.509. The list is ordered by client preference, but the server chooses — it can only offer what it actually has. Meanwhile the other direction went the client's way. That asymmetry is the entire point of having two extensions: a public server with a real certificate can still authenticate devices by bare key.
06 Where the trust actually comes from

This is the sentence to remember from the whole document, and it appears in the abstract, the introduction, and twice more in §4:

"The mechanism defined herein only provides authentication when an out-of-band mechanism is also used to bind the public key to the entity presenting the key."

RFC 7250, §1

TLS still proves possession of the private key — that part is ordinary and unchanged. What is missing is any claim about whose key it is. §4.3 and §4.4 say it directly, once for each direction: authentication "is supported only through authentication of the received SubjectPublicKeyInfo via an out-of-band method". Three such methods are named:

Public internet

DANE

The key — or its hash — is published in a DNSSEC-signed TLSA record at the name you are connecting to. The DNS name is the identifier, and DNSSEC is the binding. (RFC 6698)

Constrained devices

Pre-configuration

The key is written into firmware at manufacture and updated through the software update channel. The RFC is explicit that this is not suitable for generic web e-commerce, but is reasonable where the device software and the server endpoint are managed together.

Someone else's problem

Application layer

A protocol built on top can define its own binding — but then that specification must say how. RFC 7250 requires it: specs using this extension "need to specify how the identifier and public key are bound".

Binding is not a one-time step
Beyond establishing the binding out-of-band, an implementation "also needs to check the status of that binding". Raw public keys have no CRL and no OCSP — whatever revocation story you have lives entirely in the out-of-band channel. If that channel is a DNS lookup you cache for a week, that is your revocation window.
07 Security: what breaks, and what doesn't
The real risk

No binding → machine-in-the-middle

"Without a secure binding between identifier and key, the protocol will be vulnerable to man-in-the-middle attacks." An attacker who substitutes their own key completes a perfectly valid handshake. Nothing in TLS catches it, because nothing in TLS was asked to.

The mitigation is not in this document. It is in whatever mechanism you chose in §6 — and the RFC insists an assessment of that choice happens before deployment, not after.

The non-risk

Downgrading the certificate type

Could an attacker rewrite the hellos to force a weaker type? They can try, but they cannot finish. The extensions ride in the hello messages, and hello messages are covered by the handshake hash.

Client and server would compute different transcript hashes and reject each other's Finished. Repairing them requires the master_secret, which the attacker does not have. The tampering is detected, not merely discouraged.

What you gain, per the RFC
Lower over-the-air overhead, since a raw key is naturally smaller than a certificate; a smaller code footprint for parsing and processing; and no change at all to the cryptographic proof of private-key possession, which follows the standard procedures. The trade is narrow and explicit: you give up in-band identity, and you must replace it yourself.

Reading the first three bytes

0x30 is the DER tag for SEQUENCE. 0x81 says "the length needs one more byte", and 0x9f is that length: 159 content bytes. Add the three bytes of tag and length and the entire credential is 162 bytes.

Everything inside is the algorithm identifier (the RSA OID plus a NULL parameter) and the key itself (modulus and exponent). No subject, no issuer, no validity dates, no signature — which is exactly the 600-plus bytes an X.509 wrapper would have added.

09 Registry, and life after TLS 1.2

RFC 7250 was written against TLS 1.2 (RFC 5246), but its two extensions survived into TLS 1.3 unchanged in meaning — which is why raw public keys are still a live option today rather than a 2014 curiosity.

RegistryNameValueNote
TLS Certificate TypesX.5090 The default. Assumed when neither extension is negotiated.
TLS Certificate TypesOpenPGP1 From RFC 6091. Appears in Figure 8's example list; no longer in meaningful use.
TLS Certificate TypesRaw Public Key2 Registered by this document. The one new code point.
TLS ExtensionTypeclient_certificate_type19 Valid in both ClientHello and ServerHello. Value assigned by IANA, not stated in the RFC prose.
TLS ExtensionTypeserver_certificate_type20 Same. Both carry values drawn from the Certificate Types subregistry above.
In TLS 1.3
RFC 8446 keeps both extensions and points at RFC 7250 for their semantics, with one structural adjustment: TLS 1.3 has no select in its Certificate message, so when RawPublicKey is negotiated the certificate_list must contain exactly one CertificateEntry, holding the ASN1_subjectPublicKeyInfo. Same bytes, one more layer of framing. The extensions also move from the hellos into the encrypted portion of the handshake, which is a privacy improvement RFC 7250 never had.

The constrained-device goal aged well too: RFC 7925, the IETF's TLS/DTLS profile for the Internet of Things, builds directly on this mechanism — the smart-object case from §1 is not hypothetical.
What RFC 7250 deliberately does not do

It does not define how to get the key. DANE, LDAP, and firmware provisioning are listed as examples in the introduction and nowhere become normative. The document is a transport for a key you already trust by other means.

It does not shrink the key further. Hash-based key identification was in early drafts and was moved out after IETF 82 into what became the TLS Cached Info extension. RFC 7250 always sends the full DER structure.

It does not touch anything but the two hellos. "It does not extend or modify any other TLS message." No new cipher suites are needed; forward-secret Diffie-Hellman suites work with raw keys exactly as they do with certificates, which the RFC notes without diagramming.
